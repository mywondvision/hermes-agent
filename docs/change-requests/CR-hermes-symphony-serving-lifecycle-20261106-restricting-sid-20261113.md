## Проблема

Токен воркера сохраняет SID пользователя. Поэтому воркер проходит проверку доступа к любому объекту пользователя,
чья целостность не выше Low, — в том числе к чужому процессу Low вне своего Job. Через такой процесс он создаёт
потомка, которого не остановит kill-on-close и не увидит observer.

## Предлагаемое решение (предложение исполнителя, INFERRED; не решение владельца до его `ok`)

1. Токен воркера создаётся с списком restricting SID. Windows проверяет доступ для такого токена дважды — по
   обычным SID и по restricting SID — и даёт доступ, только если прошли обе проверки.
2. В список входят: уникальный SID попытки (вычисляется из идентификатора попытки) и общие группы, по которым
   читаются системные файлы и интерпретатор (Everyone, Users, Authenticated Users). SID пользователя и SID сеанса
   входа в список не входят.
3. В DACL по умолчанию токена воркера добавляется SID попытки, чтобы воркер работал с объектами, которые создаёт
   сам (потомки, каналы).
4. Тестовый стенд даёт SID попытки доступ к каталогу «своя копия». В production такого каталога по-прежнему нет.
5. Проверка границы до resume дополняется: токен воркера ограничен, в списке restricting SID есть SID попытки и
   нет SID пользователя и SID сеанса входа. Иначе — отказ `WORKER_BOUNDARY_UNENFORCED`.
6. Пути отката на токен без restricting SID нет: если воркер с таким токеном не запускается, запуск отказывает.

Уровень целостности Low, метки процесса owner и каталога данных, пределы Job остаются как есть. Схема журнала не
меняется. Нового демона, IPC, очереди, HTTP, планировщика и переменных окружения нет. Учётные записи, профили
AppContainer и системные настройки не создаются и не меняются.

## Запрос допуска на native-проверку (нужен владелец)

Нужен synthetic native-проход без модели: семь файлов `test_symphony_pm_windows_*.py` (без topology diagnostic),
только собственные процессы Python, retries=0. Без этого допуска native-проверки не запускаются.

Отдельный вопрос к владельцу: токен с restricting SID может не дать запуститься интерпретатору или console host,
и состав списка придётся уточнять по результату. Исполнитель просит допуск на один проход и до двух
корректирующих проходов, каждый — только после изменения состава списка restricting SID, с записью причины.
Если владелец даёт один проход, второй потребует нового допуска.

## Существенные неизвестные

- Не подтверждено, что интерпретатор Python и console host запускаются с токеном, в котором есть restricting SID.
- Не подтверждено, что воркеру без SID сеанса входа в списке хватает доступа к оконной станции и рабочему столу.
- Не подтверждено, что унаследованные capture-хендлы и дочерние процессы воркера работают при изменённом DACL по умолчанию.
- Не подтверждён формат уникального SID попытки, который система принимает в списке restricting SID.
- Группа Authenticated Users в списке оставляет воркеру чтение файлов вне профиля пользователя; без неё на этом хосте интерпретатор недоступен.
- Не подтверждено, закрывает ли restricting SID открытие чужих процессов пользователя со средней целостностью с правом завершения.
- Остаются открытыми: loopback и сеть, чтение файлов пользователя вне профиля, UI без ограничений Job, WMI и COM (не проверялись), потоки owner (открытие с правом запроса сведений).
- Процессы того же пользователя со средней целостностью по-прежнему могут продублировать хендл Job из owner.

## Риски и rollback

- Срез может оказаться невыполнимым на этом хосте: тогда результат — отказ запуска и запись причины, защита не понижается.
- Доступ SID попытки к каталогу стенда — запись в DACL каталога стенда; вне стенда DACL не меняются.
- Настоящий driver под таким токеном может не работать: это выяснится только на этапе driver, который остаётся HOLD.
- Rollback: вернуть `windows_token.py` и `windows_receiver.py` к `159a3314`; журнал, идентичности, эффекты и резервации не затронуты.
