## Исходное состояние (проверено)

- Пилоты 1 и 2: `codex exec` по подписке ChatGPT (файл авторизации в `D:\SymphonyRuntime\codex-home`) под MXC с профилем «только своя попытка» выполнил две задачи; предпроверка `codex sandbox` до модели каждый раз давала отказы вне попытки.
- Результаты обоих пилотов по решению владельца применены и закоммичены; последний — приватная ветка `94a18854`, публичная пара `afc6e073`.
- Запуск в пилотах делает отдельный сценарий стенда (`pilot_codex_exec.py`, `pilot2_codex_exec.py`), а не Symphony.
- Transport Symphony (`windows_transport`, `WindowsReceiver`) создаёт процесс только с собственным ограниченным токеном воркера (Low + restricting SID) и `CodexLauncher` поверх драйвера kit; этот путь не совместим с клиентом Codex и его песочницей MXC.
- `LifecycleOwner.submit` вызывает `launcher(ticket, request, runner)`; журнал держит одну запись запуска на namespace (`UNSETTLED_PRIOR_LAUNCH_HOLD`).

## Предлагаемое решение (предложение исполнителя, INFERRED)

1. **`CodexExecLauncher`** (новый модуль `plugins/symphony_pm/transport/codex_exec_launcher.py`) — перенос логики
   пилотов в код плагина: рабочая область попытки из `attempt_workspace` (копия коммита без `.git`, теневой
   Git-каталог); предпроверка `codex sandbox` с профилем до модели (стоп при любом доступе вне попытки или секрете
   в окружении); один `codex exec` с промптом задачи, `--json`, `--ephemeral`; зонд внутри — только наблюдение;
   capture patch и проверка в отдельной копии (`git apply`, `ruff`, тесты затронутых файлов, включая тесты с `git`).
   Результат запуска — patch, его SHA-256 и итог проверки; к рабочей копии он не применяется.
2. **Процесс клиента.** Новый провайдер `CodexClientProvider` рядом с `WindowsNativeProvider`: клиент Codex
   создаётся с токеном пользователя в Job с kill-on-close (как в пилотах); ограничение команд даёт MXC. Окружение
   клиента — явное, без имён-секретов (существующий `require_plain_environment`). Существующий путь с токеном
   воркера не удаляется и не меняется.
3. **Каталог попытки.** Корень `D:\SymphonyAttempts` (принцип Р2 согласован ранее): активная попытка всегда в
   `D:\SymphonyAttempts\active`, в профиле — одна постоянная запись на запись туда; после запуска каталог
   переименовывается в `D:\SymphonyAttempts\<attempt>` и хранится без автоудаления.
4. **Журнал.** Итог запуска (patch, SHA-256, итог проверки, расход токенов) записывается в журнал как наблюдение
   owner — основа для статуса.
5. **CLI-команда статуса** через `ctx.register_cli_command` плагина (ядро не меняется): `hermes symphony status` —
   только чтение журнала: запуски, состояние, путь и SHA-256 patch, итог проверки.
6. **Сборка** `codex_exec_transport(...)` рядом с `windows_transport`: те же `TransportBootstrap`,
   `WindowsOwnershipGuard`, `WindowsQueryObserver`, журнал и разрешения; `QualificationRecord` фиксирует путь и
   SHA-256 `codex.exe`, `CODEX_HOME` и SHA-256 его `config.toml`.

## Acceptance

- A1 (fixture). Полный путь `submit` → launcher → результат проходит с поддельным исполняемым файлом Codex
  (Python-скрипт): создание попытки, предпроверка, запуск, capture, проверка, запись в журнал; любой отказ
  предпроверки — запуск модели не происходит.
- A2 (fixture). `hermes symphony status` показывает запуск, patch и итог проверки из журнала и ничего не пишет.
- A3 (native, один запуск с моделью). Через `LifecycleOwner` с тестовым источником разрешения (как в стенде
  serving): реальный `codex exec` выполняет небольшую задачу; граница — как в пилотах; итог виден в
  `hermes symphony status`.
- A4. Fixture-набор Symphony и `ruff` по изменённым файлам проходят; хост до и после без изменений.

## Out of scope

- Production-источник разрешения пользователя (шаг 3), доверенный `get_status` инструмента (шаг 4 — команда CLI
  читает журнал напрямую), cancel/stop (HOLD), закрытие попытки и следующая задача (шаг 5), автоматическое
  применение patch (шаг 6), голос.
- Установка transport в живую сессию Hermes по умолчанию: сборка явная и ничего не включает сама.
- MCP, web search, коннекторы, сеть команд; изоляция от процессов того же пользователя.

## Существенные неизвестные

- Хватит ли одной постоянной записи профиля (`active`) или Codex понадобится запись по точному пути попытки.
- Как журнал должен хранить итог проверки, чтобы шаг 4 мог выдать его как доверенный статус без переделки.
- Поведение `LifecycleOwner` при запуске, который длится десятки минут (лимит, наблюдатель).

## Риски и rollback

- Новый провайдер создаёт процесс с токеном пользователя — это осознанное решение владельца для клиента Codex;
  путь с токеном воркера остаётся для прочих случаев. Rollback: удалить новые модули; существующий transport не
  меняется.
- `D:\SymphonyAttempts` создаётся впервые; rollback — удалить пустой корень.
