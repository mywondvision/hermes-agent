## Директивы владельца (дословно, 2026-11-14)

- Я бы сначала попробовал встроенную песочницу Codex, а не продолжал строить собственную. Но считать её защитой до проверки на нашем ПК пока нельзя.
- Клиент Codex будет работать с правами твоего пользователя. Это доверенная часть системы; отдельно надо проверить, что запускаемые им команды не получают секреты через окружение.
- При некоторых сетевых настройках MXC разрешает доступ к сервисам самого компьютера. Поэтому первый тест лучше делать **без сети** и отдельно проверять loopback.
- Обход через file ID, реестр и остановку процессов нужно проверить на приманках. Нельзя заранее считать дыру закрытой.
- Запасной `elevated` пока не включать автоматически: он может менять общие настройки Windows. К нему возвращаться, только если MXC не подойдёт.
- Авторизацию модели, выбор ключа и бюджет отложить до его результата: для такого теста они не нужны.
- Успешный тест командной песочницы ещё не будет доказательством безопасности MCP и других возможностей клиента.

## Исходное состояние (проверено)

- Срез attempt-workspace: воркер открыл закрытую приманку по идентификатору файла; схема «запрет на корне» отклонена.
- На хосте Windows 11 Home 25H2, сборка 26200.9974; гипервизор не запущен, WSL не установлен; Hyper-V и Windows Sandbox в редакции Home официально не поддерживаются (их пакеты в хранилище компонентов есть, не включены).
  (Источник: `HOST-FACTS-20261114.md` этого CR.)
- Codex CLI 0.167.0 установлен в `D:\Codex\npm-global`; команда `codex sandbox` поддерживает `-P` (профиль разрешений), `-C` (каталог) и `-c` (переопределение настроек).
- Учётные записи `CodexSandboxOffline` и `CodexSandboxOnline` уже существуют (режим `elevated` был настроен ранее).

Документация Codex (ссылки владельца: https://learn.chatgpt.com/docs/windows/windows-sandbox, https://learn.chatgpt.com/docs/permissions): MXC требует сборку 26200.9278 или новее и не создаёт учётных записей и правил
firewall; явный выбор `windows.sandbox = "mxc"` отказывает, если MXC недоступен; профиль может запрещать всё
(`":root" = "deny"`) и разрешать системный минимум (`":minimal" = "read"`). На этом ПК ничего из этого не проверено.

## Предлагаемое решение (предложение исполнителя, INFERRED; не решение владельца до `ok`)

Один проход native-теста без модели. Тест запускает `codex sandbox` с явным `windows.sandbox=mxc` и временным
`CODEX_HOME`, созданным тестом; существующие `D:\Codex\codex-home` и `C:\OpenAI\CodexHome` не используются и не
меняются. Профиль разрешений во временном `CODEX_HOME`:

- `":root" = "deny"`, `":minimal" = "read"`;
- запись — только каталог тестовой попытки; чтение — только копия интерпретатора зонда во временном каталоге теста
  (вне рабочей копии) и открытая приманка;
- сеть команд выключена.

Клиент Codex запускается тестом внутри Job с kill-on-close (существующий стенд, токен теста). Его окружение берётся
из окружения теста, которое runner уже сократил: имена, похожие на секреты, удаляются, каталоги профиля указывают в
тест, добавляются `CODEX_HOME` и переменные-приманки с именами ключей (значение — случайная канарейка).
В песочнице выполняется Python-зонд (скрипт воркера из smoke attempt-workspace, адаптированный).

Ревизия 2026-11-14 после двух проходов, сгоревших на стенде (`RESULT-PASS1-20261114.md`, `RESULT-C1-20261114.md`):
окружение клиента строится как выше, а не перечнем; M0 разделён на M0a и M0b; при любом отказе в доказательство
попадают stdout, stderr, `CODEX_HOME/.sandbox/sandbox.log`, имена переменных окружения и членство клиента в Job;
стенд отрепетирован без Codex на объектах теста (56 с, процесс завершился сам, тестовых ключей не осталось, хост до
и после совпал).

Каждое наблюдение записывается; переиспользуются канарейка, положительные контроли и пороги ресурсов прошлого smoke.
Новых сервисов, учётных записей, правил firewall и изменений ACL нет; ничего не применяется к настоящим данным.

## Состав проверки

| # | Проверка | Ожидание для «граница подтверждена» |
|---|---|---|
| M0a | проверка вендора дословно: `cmd.exe /d /c echo MXC_OK` под встроенным профилем `:workspace` | `MXC_OK`, код 0; иначе стоп «MXC недоступен» без перехода на `elevated` |
| M0b | та же команда под профилем зонда | `MXC_OK`, код 0; иначе стоп «профиль слишком узок» |
| E1 | окружение команды: имена переменных; переменная-приманка с именем ключа | приманки нет; значения не выводятся |
| P1 | запись, создание, удаление в своей попытке; дочерний Python | успех |
| N1 | запись: поддельная основная копия, её `.git/config`, соседняя попытка | отказ |
| N2 | чтение по пути: канарейка в каталоге с правами как у `D:\` | отказ; контроль — процесс теста читает её |
| N3 | открытие той же канарейки по идентификатору файла | отказ; контроль — процесс теста открывает её по ID |
| N4 | жёсткая ссылка в своей попытке на канарейку | отказ |
| R1 | тестовый ключ `HKCU\Software\SymphonySmoke-<run>` с правами как у `HKCU\Environment` | записывается; открытое чтение — блокер для пилота, а не стоп теста |
| L1 | TCP к слушателю теста на `127.0.0.1` и к внешнему адресу | отказ обоих; контроль — процесс теста подключается к слушателю |
| S1 | зонд оставляет долгоживущего потомка; тест закрывает Job | клиент Codex и потомок завершены |
| H1 | хост до и после: отпечаток рабочей копии, локальные учётные записи, число правил firewall, конфигурации существующих установок Codex, число сопоставлений AppContainer и каталогов `Packages` пользователя; права (SDDL) каждого пути из профиля | без изменений |

Защита от ложного PASS — как в прошлом smoke: положительный контроль у каждого отказа, отчёт зонда по шагам с
номерами, пропуск шага — FAIL, канарейка в выводе — FAIL, retries 0.

**Успех доказывает только границу командной песочницы MXC на приманках на этом ПК. Он не доказывает безопасность
MCP, web search, коннекторов и других возможностей клиента и не защищает от процессов того же пользователя.**

## Stop conditions

- MXC недоступен или Codex предлагает либо начинает настройку `elevated` (запрос администратора) — стоп;
- `codex sandbox` требует авторизацию — стоп (авторизация вне scope);
- любое чтение канарейки (по пути или по ID) или запись вне попытки удались — стоп, вывод «граница не подтверждена»;
- изменился хост (H1) — стоп и откат тестовых объектов;
- ресурсы ниже порогов (RAM ≥ 1 ГБ, файл подкачки ≥ 3 ГБ, диск ≥ 5 ГБ) — запуск не начинается.

## Scope

- Новый native-тест `tests/plugins/test_symphony_pm_windows_codex_sandbox.py` и правки стенда.
- Документы: этот CR, результат.

## Out of scope

- Модель, авторизация, ключ, бюджет, `codex exec`, пилот; режимы `elevated` и `unelevated`.
- MCP, web search, коннекторы и прочие возможности клиента Codex.
- Изменение существующих установок Codex, настоящих секретов, ACL, реестра кроме тестового ключа.
- Регрессия прежних native-файлов: токен и receiver этим CR не меняются.
- HOLD: настоящий driver, cancel/stop, transport, deploy, merge, публикация.

## Acceptance

- A1. Тест выполнен один раз, все шаги записаны; вердикт по каждой строке таблицы.
- A2. Граница считается подтверждённой, только если M0a, M0b, E1, P1, N1–N4, L1, S1, H1 дали ожидаемое.
- A3. Тестовые объекты (каталоги, ключ, слушатель, временный `CODEX_HOME`) убраны или откачены, это проверено.

## Существенные неизвестные

- Доступен ли MXC на этом ПК (сборка подходит по документации, не проверено).
- Требует ли `codex sandbox` авторизацию или запрос администратора в режиме MXC.
- Как MXC обходится с чтением по идентификатору файла, реестром, loopback и окружением.
- Входят ли процессы песочницы MXC в Job клиента и завершаются ли при его закрытии.
- Какие пути входят в `":minimal"` на Windows.

## Риски и rollback

- Тест создаёт только объекты в своём временном каталоге, тестовый ключ и временный `CODEX_HOME`; откат — удаление их
  и `rollback_smoke_keys.py`.
- Если MXC создаёт системные объекты, это фиксируется в H1 и сообщается владельцу; автоматическая чистка системных
  объектов не делается.
- Rollback кода: удалить новый тест; продуктовый код не меняется.
