## 1. Общие правила для всех CR

- **Допуски не наследуются.** На 2026-11-19 у исполнителя нет ни одного допуска: «Ок на все» шага 2 израсходован.
  Каждый native-прогон, запуск модели, правка хоста или профиля Codex, правка ядра, push — отдельное слово владельца
  для конкретного CR. Остановка до модели не даёт права на повтор.
- Виды допусков: **native** — прогон на этом хосте без модели; **model** — запуск `codex exec` по подписке;
  **host** — правка каталогов runtime и попыток Symphony, профиля MXC, конфигурации живого профиля Hermes или
  перезапуск gateway; **core** — правка файлов вне `plugins/symphony_pm/` и `tests/`; **push** — push в fork по
  URL. По умолчанию ничего не выдано.
- **Формула native-допуска по умолчанию** (как в прежних CR): один проход и до одного корректирующего;
  корректирующий — только после изменения стенда или кода, причина записывается в RESULT. CR называет точный
  список файлов тестов прохода. Другое число — только если оно названо в CR и подтверждено владельцем.
- Каждая правка `config.toml` профиля меняет его SHA-256 → новая квалификация (F10). Бэкап до правки, как в шаге 2.
- Native-прогоны идут **одной очередью** (мало RAM): ожидание памяти ≥ 1.1 ГБ, `scripts/check` — при ≥ 4 ГБ.
  Параллелятся только fixture-работа, код и документы.
- Код — пара коммитов приватная + публичная (redacted), автор — no-reply; документы и доказательства — в ветку
  документов `claude/hermes-symphony-codex-auth-20261114`. Публичные материалы: хэш SDDL/SID, без имён переменных
  окружения и путей с именем пользователя. Push только по слову «push», только в fork, никогда в `origin`.
- Тесты — `scripts/run_tests.sh`; новые native-тесты — `@pytest.mark.platforms("windows")`; контрактные тесты
  поведения, не чтение исходников; ratchet размеров; новое поведение — в sibling-модуле.
- Одобренный CR не переписывается: отступления — в RESULT и в следующий CR.
- **Выход каждого CR:** RESULT в `docs/audits/<cr-id>/`, обновлённые метки в архитектуре (PROPOSED → CONFIRMED с
  путём доказательства или запись об отказе от решения), fixture-набор Symphony зелёный (база: 15 файлов, 257
  тестов).

## 2. Порядок и отличие от дорожной карты handoff

Дорожная карта handoff (§7): 2.1 → разрешение → статус → cancel/settle → apply → живая сессия → релиз. Изменения:

1. **Журнал v2 и восстановление — первыми.** После первой попытки любой рестарт gateway и любая перезагрузка
   хоста оставляют namespace без владельца, пути освобождения нет (F5, F15, F16 — CONFIRMED). Это предусловие
   всего остального, а не «шаг 5».
2. **Стоп и settle раньше статуса и подтверждения** (как в ред. 1): статус должен показывать терминальные
   состояния, а отмена через процессы MXC сейчас не работает (F7).
3. **Проверка в песочнице (находка 4) вынесена из критической цепочки** в параллельную линию: она блокирует только
   apply и запуск с моделью.
4. Новые CR, которых нет в §7: **CR-0** (что значит релиз — решение до начала кода), **CR-0b** (перенос adapter в
   плагин — выбран владельцем по Q1), **CR-5** (асинхронный запуск), **CR-8a** (стенд с моделью до живой сессии),
   разделение шага 7 на **CR-9a** (включение без модели) и **CR-9b** (пилот); ред. 3: **CR-H** (подготовка
   арендованной Windows-машины, Q8), **CR-7b** (профиль с терминалом в пределах папки, Q11; до релиза),
   **CR-V1** (голос как канал ввода, Q9).
5. **Независимое ревью границ — до включения в живой gateway** (выход CR-8a), а не только в релизе.

### Параллельность для субагентов Codex

Сейчас весь launcher — один файл (`codex_exec_launcher.py`, 484 строки): зонд, предпроверка, запуск, capture,
проверка и переименование попытки. Чтобы линии не правили один файл, **первый коммит CR-1 — разнесение launcher
на siblings без изменения поведения** (зонд и `probe_ok`; owner-check; ядро запуска), fixture-набор зелёный. После
него линия A правит только siblings зонда и проверки и профиль MXC; линия B — `schema.py`, `journal.py`,
`lifecycle.py`, новый наблюдатель, ядро запуска.

| Что можно делать параллельно | Условие |
|---|---|
| CR-1 (линия A) и CR-2 (линия B), два субагента | после `ok` на оба CR и после коммита разнесения launcher |
| CR-3 (линия A) рядом с CR-4 … CR-7 (линия B) | CR-1 закрыт; общие файлы только через слияние в конце CR |
| CR-0 | сразу; не код |
| Черновик PlanResolver и обработчиков `/symphony` (CR-7) на fixture в новых модулях | без правки `approval.py`/`service.py`; вливается после CR-6 |
| Ревью каждого CR | отдельный read-only субагент, не автор |
| CR-H (линия H) рядом с любой линией | после `ok` на CR-H и host-допуска; аренду и вход в подписку делает владелец |
| CR-V1 и CR-7b рядом с CR-8 | CR-7 закрыт; CR-V1 правит только обработчики `/symphony` и контракт голоса |
| native и model | никогда: одна очередь на хост; порядок очереди — CR-1, CR-2, CR-4, CR-3, CR-5, CR-7, CR-8, CR-8a. После CR-H native-прогоны можно переносить на арендованную машину (своя очередь, RAM-ограничение этого хоста там не действует) |

### CR-2. Журнал v2: терминальные состояния, наблюдения, восстановление (находки 5, 6; D2, D8, D13)

- **Цель.** Журнал, в котором namespace освобождается по доказательству и владелец стартует после рестарта и
  перезагрузки.
- **Scope.** (1) Схема v2 с явной миграцией v1→v2 (только схема, состояний не выводит): терминалы запуска
  `NOT_STARTED`, `STOPPED(proof)`, `HELD_UNKNOWN`, `RELEASED_BY_OWNER` в `serving_launches`; append-only
  `serving_observations`. (2) Удержание — «есть нетерминальная строка», наблюдатель покрывает только
  нетерминальные строки. (3) Атомарный переход `LAUNCH_INTENT → NOT_STARTED`, после которого create невозможен.
  (4) Reconcile при старте владельца по D13 (решение Q13): смерть владельца того же boot и смена boot. Если Q13 =
  нет — те же строки переходят в `HELD_UNKNOWN`, но владелец всё равно стартует. (5) Статус CLI читает v2.
  (6) Запись наблюдений; путь повторного capture из сохранённой попытки (D8) как функция владельца — без
  пользовательской команды (она в CR-6).
- **Out of scope.** Остановка Job и доказательство `JOB_EMPTY` (CR-4); команды человека (CR-6); статус инструмента.
- **Acceptance.** A1 fixture: миграция сохраняет все строки, повтор — no-op, неизвестная версия отклоняется, v1 без
  миграции не открывается. A2 fixture: второй запуск в namespace проходит после `NOT_STARTED`, после `STOPPED`,
  после `RELEASED_BY_OWNER`; при `HELD_UNKNOWN` — отказ. A3 fixture: владелец стартует над журналом (i) со
  связанной строкой умершего предшественника, (ii) с записью владельца другого boot — и в обоих случаях ставит
  состояние по правилу Q13; живой предшественник — по-прежнему отказ. A4 fixture: `NOT_STARTED` и `claim_create`
  взаимоисключающи при гонке двух потоков. A5 fixture: повторный capture пишет новое наблюдение, первичная запись
  не меняется. A6 native без модели: повторный capture сохранённой попытки A3 на **копии** её журнала и каталога
  данных даёт patch с SHA-256 `2eb08197…` (как офлайн-capture шага 2).
- **Verification.** Тесты схемы на реальных файлах SQLite во временном доме Hermes; существующие native-тесты
  краша, закрепляющие прежнее удержание (F16), обновляются в этом CR и **не запускаются** без допуска — их прогон
  входит в native-проход CR-4.
- **Допуски.** native: один проход A6 (без корректирующего — при неудаче разбор в RESULT). host: нет (работа на
  копии; исходная попытка A3 и её журнал не меняются).
- **Зависимости.** Решение Q13 принято (да). CR-0b.
- **Риски, rollback.** Миграция необратима для файла → копия журнала до миграции. Ложный терминал → запуск рядом

- **Допуски.** native: один проход (файлы A2–A4) + один корректирующий. host: нет (профиль MXC не меняется).
