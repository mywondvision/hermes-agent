## Граница угроз и что остаётся открытым

Защищаемся от **воркера и его потомков**: они не изменяют чужие копии и не читают объекты, закрытые запретом
для SID класса воркеров.

Открыто и этим CR не решается (не объявлять решённым):

- **Процессы того же пользователя не изолированы.** Любой процесс пользователя со средней или низкой целостностью может писать в каталог попытки, подменить patch до проверки, открыть воркер, продублировать хендл Job.
- **Защита настоящих корней не применяется и не доказывается:** чтение файла учётных данных на D, `.env` других копий и `HKCU\Environment` воркером остаётся открытым до отдельного шага.
- **Учётные данные настоящего driver:** способ доставки не определён; в каталог попытки они не копируются.
- **Настоящий driver** под этим токеном не запускался и остаётся HOLD.

Более сильная граница (не реализуется): список разрешений вместо запретов (LPAC) — отдельный CR; защита от
процессов пользователя — другой субъект (отдельная учётная запись или VM). На этом хосте (Windows 11 Home)
Hyper-V и Windows Sandbox недоступны, WSL не установлен.

## Предлагаемое решение (предложение исполнителя, INFERRED; не решение владельца до `ok`)

### Механизм (код)

1. **Рабочая область попытки** `<корень>\<attempt>\` с подкаталогами `src`, `home`, `temp`; создаётся только на
   пустом месте. Доступ на изменение — SID пользователя и SID этой попытки. Метка Low (OICI, no-write-up) — только
   на этом новом каталоге.
2. **Копия дерева:** `git -c core.autocrlf=false archive <SHA>` из основной копии процессом owner (только чтение
   `.git`), распаковка в `src`; `.git` в копию не попадает. Теневой Git-каталог owner — в его приватном каталоге.
3. **SID класса воркеров** (`S-1-9-…` из фиксированной строки) добавляется в список restricting SID;
   `require_boundary` требует точный список. У токена снимается привилегия обхода проверки прохода.
4. **Проверка чтения до resume:** для перечня защищаемых объектов (в smoke — только приманки) запись DENY на месте
   и `AccessCheck` токеном воркера даёт отказ; иначе `READ_BOUNDARY_UNENFORCED`.
5. **Окружение только явное** (HOME, USERPROFILE, APPDATA, LOCALAPPDATA, TEMP, TMP внутри попытки; SYSTEMROOT,
   WINDIR; PATH из списка); имена с признаками секрета — отказ до создания процесса.
6. **Capture после остановки:** обход `src` без следования ссылкам, отказ на точку повторного разбора
   (`ATTEMPT_REPARSE_POINT`) и файл с несколькими жёсткими ссылками (`ATTEMPT_HARDLINK`); diff теневым
   Git-каталогом без hooks, fsmonitor и системного/глобального config; patch `--binary`; политика путей (без
   `.git*`, `.gitattributes`, `.gitmodules`, hooks, смены режима, сверх лимита размера); `git apply --check` на
   свежей копии `<SHA>`; SHA-256 patch в журнал наблюдений. Patch — данные, не применяется.
7. **Снимок и откат запретов** (один модуль для приманок и, позже, для настоящих корней): снимок SDDL объекта
   (без значений реестра), журнал `planned → applying → applied → reverting → reverted`, применение и откат
   идемпотентны, запись без распространения на дочерние объекты, откат удаляет только записи SID класса и
   сверяет SDDL со снимком; при расхождении по другой причине снимком не перезаписывает.

### Размещение в production (предложение; сейчас не создаётся и не меняется)

- `D:\SymphonyAttempts` — корень попыток с защищённым DACL (пользователь, SYSTEM, администраторы), без Users и
  Authenticated Users. `D:\SymphonyRuntime` — автономный интерпретатор воркера вне `D:\AI` (только чтение).
- **Low только на новом каталоге попытки.** Воркер с целостностью Low пишет лишь в объекты с меткой Low; объект
  без метки считается Medium. Метки существующих объектов не понижаются: это открыло бы их любому Low-процессу
  пользователя, а записанное исполнял бы процесс Medium.
- **Хранение без автоудаления.** После capture попытка «замораживается»: метка поднимается до Medium с
  no-write-up, запись SID попытки снимается; patch и манифест — в приватный каталог данных плагина. Удаление —
  только решением владельца.
- **Откат размещения:** удалить пустой корень и runtime-каталог; удержанные попытки не удаляются без решения
  владельца; запреты — откатом из п. 7.

### Пороги свободного места (один смысл у каждого)

- **5 ГБ — останов smoke.** Smoke создаёт три попытки, одну полную копию дерева (около 230 МБ), две малые копии,
  свежую копию для `git apply --check` и теневой Git-каталог — оценка не больше 1 ГБ; 5 ГБ дают пятикратный
  запас. Проверяется на томе временного каталога теста непосредственно перед проходом.
- **50 ГБ — нижняя граница для создания новой попытки в production** при хранении без автоудаления (попытки
  накапливаются по 230+ МБ). К этому smoke не относится и реализуется только с размещением в production.

## Первый smoke: тестовые приманки

### Что создаёт тест (только свои объекты)

- Во временном каталоге теста на D: корень-приманка с наследованием как у `D:\` (Users чтение, Authenticated
  Users изменение) и вложенный файл-канарейка со случайной строкой; запись DENY для SID класса на корне приманки
  через модуль п. 7.
- Тестовый ключ `HKCU\Software\SymphonySmoke-<run>\Env` с DACL по образцу `HKCU\Environment` (чтение RESTRICTED)
  и записью DENY для SID класса. Ключ удаляется в конце теста с проверкой; при прерывании его находит и удаляет
  скрипт отката по префиксу `SymphonySmoke-`.
- Поддельная «основная копия» с `.git`, соседняя попытка, каталог данных плагина (существующий `guard_owner`).
- Корень попыток — временный каталог теста; `D:\SymphonyAttempts` и `D:\SymphonyRuntime` не создаются.

Настоящие корни, `HKCU\Environment`, существующие worktree и `.git` не меняются.

**Защита от ложного PASS:** у каждого отказа N1–N4 есть положительный контроль — процесс теста открывает тот же
объект тем же путём или по тому же идентификатору; засчитывается только код 5, не 2 и не 3. Воркер отчитывается
по каждому шагу с порядковым номером, пропуск шага — FAIL. Канарейка в выводе воркера, capture или patch — FAIL.
Манифест хэшей основной копии до и после. retries 0, без `-k`; строки тестов и исходники сохраняются.

**Успех smoke доказывает механизм на приманках и не означает, что настоящие секреты защищены.**

## Риски и rollback

- Smoke меняет только объекты теста (временные каталоги, тестовый ключ реестра); откат — модулем п. 7 и
  удалением тестового ключа; при прерывании — скрипт отката по префиксу `SymphonySmoke-`.
- Rollback кода: вернуть `plugins/symphony_pm/transport/` к `9ef69db2`; журнал и резервации не затронуты.
- Срез может оказаться невыполнимым (N3 или N4 удались): результат — запись причины; тогда схема «запрет на
  корне» отклоняется, защита не понижается.

## Пакет решения для допуска smoke (нужен владелец)

| Решение | Рекомендация | Требует допуска |
|---|---|---|
| Р1. Запреты | в smoke — только на приманках; настоящие корни — отдельный шаг после результата N3/N4 | `ok` на CR |
| Р2. Размещение и Low | `D:\SymphonyAttempts`, `D:\SymphonyRuntime`, Low только на новом каталоге попытки | сейчас — только согласие с принципом; создание — отдельно |
| Р3. Хранение | без автоудаления, заморозка после capture, порог 50 ГБ в production | сейчас — согласие с принципом |
| Р4. Smoke | один проход: новый файл + семь прежних, retries 0, дерево `0a46b771`, пороги перед стартом | реализация по CR и один native-проход; корректирующий — только отдельным словом |
