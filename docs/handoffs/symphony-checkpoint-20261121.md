# Hermes Symphony · чекпоинт трёх сессий · 21 ноября 2026

Этот чекпоинт предназначен для продолжения под другим аккаунтом в том же рабочем каталоге. В fork три ветки: `checkpoint/symphony-20261121` для координатора, `checkpoint/symphony-20261121-windows` и `checkpoint/symphony-20261121-linux` для кандидатов. Код двух платформ проверялся на разных стадиях плана. Сохраните их раздельно до интеграции.

## Цели

Каждая из трёх новых сессий получает одну постоянную цель. Сначала прочитать `get_goal`. Если цели ещё нет, создать её с текстом своей роли и сверить результат. Уже существующую подходящую цель продолжить. Назначения CR и фактический статус брать из следующего раздела.

**Координатор.** Довести Hermes Symphony в fork до выпуска с двумя проверенными вариантами исполнения: локальным Windows/MXC и удалённым Linux на арендованной ВМ. На обеих платформах владелец может поставить задачу из чата или голосом, текстом подтвердить точный план, увидеть статус и остановить работу с проверяемым доказательством. После сбоя система восстанавливает состояние и позволяет повторно собрать patch. Только по команде владельца проверенный результат становится коммитом Robot в symphony/<job>. Сравнить производительность на одинаковой нагрузке. Для выпуска провести пять реальных задач на согласованной платформе, получить зелёный scripts/check и независимое ревью без открытых HIGH, проверить публичные материалы. Merge — по отдельному слову владельца.

**Windows.** Довести локальный маршрут Hermes → Symphony на Windows/MXC до приёмки выпуска по согласованной матрице, подтвердить чат и голос, текстовое решение владельца, статус, остановку, восстановление, повторный сбор и Robot apply в рамках допусков каждого CR и передать главному архитектору проверяемые результаты. Ближайший незакрытый критерий — A6 в CR-7. Указание «ближайший этап — CR-5» в старой цели относилось к моменту её создания.

**Linux.** Подготовить и принять удалённый Linux-маршрут Hermes Symphony по общей матрице выпуска: исправить и независимо проверить офлайн-кандидат, при выполнении согласованных условий квалифицировать ВМ и подтвердить эксплуатационные сценарии и пять задач. Соблюдать отдельные допуски владельца и доказательства каждого этапа.

## Первое действие после входа

Из корня исходного worktree в PowerShell выполните `git fetch --no-tags https://github.com/mywondvision/hermes-agent.git refs/heads/checkpoint/symphony-20261121:refs/remotes/symphony-checkpoint/20261121`. После успешного fetch выполните `& .\.artifacts\handoff-20261121\start-symphony.ps1 -CheckpointRef refs/remotes/symphony-checkpoint/20261121`. Локальная копия скрипта совпадает с `scripts/start-symphony-checkpoint.ps1` в ветке координатора. В трёх окнах появятся отдельные интерактивные сессии нового аккаунта. Они сообщат роли и идентификаторы в начале работы.

## Состав публикации и восстановление кода

Каждая платформенная ветка содержит изменения кандидатного кода относительно ранее опубликованного `e8f2879d1efeabb0d0e66f46eed3243f9390b81a`. Один исторический файл `.artifacts/live-smoke-20261106/smoke.py` оставлен в версии публичной базы. Его три правки импорта и путей представлены в `docs/handoffs/symphony-smoke-20261121.patch` ветки координатора. Это сохраняет полный результат без повторной публикации локальных путей в новом файле. Точные деревья обоих кандидатов проверены восстановлением патча в отдельных индексах Git. Оригинальные испытанные коммиты остаются в локальных копиях.

При необходимости восстановления на другой машине получите три ветки в отдельный чистый клон. Создайте отдельный worktree от ветки нужной платформы. В этом worktree выполните в Git Bash следующие команды:

```bash
git show origin/checkpoint/symphony-20261121:docs/handoffs/symphony-smoke-20261121.patch | git apply --index --unidiff-zero -
git write-tree
```

Сверьте результат с хэшем дерева в разделе «Локальные доказательства». В исходном общем worktree такая операция не требуется: там уже лежат испытанные версии. Журналы, идентификаторы прежних аккаунтов и аренды, образы и пользовательские незакоммиченные файлы остаются локальными.

## Распределение работы

1. Координатор сверяет актуальные сообщения владельца, состояние предыдущих сессий и роли трёх новых сессий. Он единственный распоряжается арендой. До внешнего действия сверить состояние по точному идентификатору. Согласованное письмо в поддержку привязано к конкретному отправителю; локальный handoff содержит адрес и тему для проверки отправленных. При недоступной почте оставить запрос в ожидании.
2. Оба подоркестратора сверяют свою рабочую копию, тестовый SHA и журнал. Общий каталог сохраняет пользовательский checkout и индекс. Для реализации использовать выделенную рабочую копию своего направления. Повторно запускать исполнителей на принятом результате не требуется.
3. В рамках согласованного CR исполнитель — `gpt-6.2-astra/high`, независимый технический рецензент — `gpt-6.2-astra/xhigh`. Для контекстного ревью текста CR разрешён один read-only `gpt-6.2-sol/high`. Три управляющие сессии запускаются в одном рабочем каталоге. Четвёртый координатор или второй арендатор не требуется.
