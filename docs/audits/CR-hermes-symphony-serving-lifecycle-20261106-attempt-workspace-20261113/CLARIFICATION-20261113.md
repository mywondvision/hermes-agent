### Наследование

Запись без флагов OI/CI и запись через `SetFileSecurityW`/`RegSetKeySecurity`: меняется DACL только этого
объекта, дочерние объекты не перезаписываются. Следствие: `AccessCheck` на файле внутри по-прежнему говорит
«разрешено»; закрывает только проверка прохода при открытии по пути, поэтому у токена воркера должна быть снята
привилегия обхода прохода. **Гипотезы, не доказаны:**

- открытие по идентификатору файла (`OpenFileById` с хендлом своего каталога на том же томе) может обойти
  проверку прохода; идентификаторы NTFS перебираемы. Если обход работает — схема «запрет на корне» не годится,
  и остаётся только наследуемый запрет на конкретных каталогах секретов (с переписыванием их поддерева);
- создание жёсткой ссылки на чужой файл (по нынешним правилам Windows нужна запись атрибутов цели — ожидается
  отказ);
- Python и `git.exe` стартуют без привилегии обхода прохода.

### Влияние

- Обычные процессы пользователя, другие сеансы и учётные записи (на хосте 3 включённых, 2 из них в
  CodexSandboxUsers; активных других сеансов нет): SID класса в их токенах нет — запись DENY к ним не
  применяется, доступ не меняется.
- Будущие попытки: все получают тот же отказ (это цель). Если попытке нужен ввод из закрытого корня (kit,
  другая копия), owner копирует его в каталог попытки.
- Новые каталоги верхнего уровня D: создаются без записи. Проверка до resume должна перечислять верх `D:\` и
  отказывать при каталоге без записи — то есть любой новый каталог блокирует запуск до решения владельца.
- Explorer покажет «неизвестную учётную запись S-1-9-…»; её удаление вручную молча снимает защиту — ловит
  только проверка до resume. `robocopy /COPYALL` перенесёт запись в копию (вреда нет).
- Песочница Codex уже держит на этом хосте свои записи (в т.ч. DENY на запись в `.git` для своих SID) —
  наши записи с ними не пересекаются; установку Codex не трогаем.

### `D:\AI` и исключения

`D:\AI` — родитель всех рабочих копий, `envs`, `preserve`, `repos`. Запись на самом `D:\AI` не меняет DACL ни
одной рабочей копии и ни одного файла внутри; меняется эффективный доступ только для токенов с SID класса.
Защитить `.env` других копий без записи на родителе (`D:\AI` или `D:\AI\worktrees`) можно только записью на
каждой копии (100+ объектов) — хуже. Решать владельцу, укладывается ли это в «не меняй права worktree».

Следствие для исключений: интерпретатор воркера сейчас — venv в `D:\AI\envs\…`, его база внутри этой копии
(`…\.artifacts\test-appdata\uv\python\cpython-3.14-…`, факт по `pyvenv.cfg`). При запрете на `D:\AI` нужен
отдельный автономный интерпретатор вне `D:\AI` (кандидат `D:\SymphonyRuntime`, только чтение). Корень попыток
тоже вне закрытых корней. `git.exe` на C: не затрагивается.

## 2. Обратимый план (для шага применения к настоящим корням; не для первого smoke)

1. **Снимок.** Для каждого объекта: путь/ключ, SDDL владельца, группы и DACL, SHA-256 SDDL, время. Значения
   реестра не читаются и не сохраняются. Файл — в приватном каталоге owner (SDDL содержит SID пользователя, в
   репозиторий не попадает).
2. **Журнал.** Состояния объекта: `planned → applying → applied → reverting → reverted`; запись до и после
   каждого шага.
3. **Применение (идемпотентно).** Нет записи для SID класса → DACL = запись DENY + прежние записи в каноническом
   порядке → запись без распространения → чтение назад. Проверки: добавилась ровно одна запись; DACL без неё
   совпадает со снимком; `AccessCheck` токеном воркера — отказ; обычным токеном — как до изменения.
4. **Откат (идемпотентно).** Удалить только записи с SID класса, записать, сверить SDDL со снимком. Если SDDL
   расходится по другим причинам (кто-то менял права) — снимком не перезаписывать, показать разницу владельцу.
5. **Сбой или прерывание.** Запись одного объекта атомарна. При перезапуске объект в `applying`/`reverting`
   проверяется по факту и доводится или откатывается. Откат дополнительно сканирует весь перечень на
   «лишние» записи SID класса — на случай потери журнала.
6. **Репетиция.** Применение и откат сначала проверяются на тестовых объектах (временный каталог и временный
   ключ под `HKCU\Software\<тест>`), и только потом — с отдельного допуска — на настоящих корнях.

## 4. Зачем Low именно на новом каталоге

Воркер — процесс с целостностью Low. Windows запрещает ему запись в любой объект с меткой выше Low; объект без
метки считается Medium. Поэтому писать он может только туда, где метка Low. Прежний запрет касается
существующих объектов: понизить метку рабочей копии или `.git` значило бы открыть их на запись любому
Low-процессу пользователя (не только нашему), а записанное потом исполнял бы процесс Medium. Новый каталог
попытки — отдельный объект, создан для одной попытки, его DACL пускает только пользователя и SID этой попытки.
Остаточный риск: Low-процессы того же пользователя проходят DACL по SID пользователя и могут писать в
каталог попытки — это та же неизолированность процессов пользователя.

Альтернатива без Low (воркер Medium с ограниченным токеном без Authenticated Users) отбрасывает уже доказанный
слой целостности и требует заново доказать все native-свойства — не рекомендую.

**Хранение (факт):** D: — NTFS, фиксированный, исправен, 953,9 ГБ, свободно 693,7 ГБ; C: — 4,2 ГБ, попытки на C:
не размещать. Одна попытка ≈ 230 МБ копии + patch. Предложение: после capture «заморозить» попытку — поднять
метку на Medium (no-write-up) и снять запись SID попытки; patch и манифест — в приватный каталог данных плагина
(метка NRNW). Это повышение, а не понижение целостности. Автоудаления нет; квота и порог свободного места
(например, стоп при < 50 ГБ на D:) — проверка до создания попытки.

## 5. Состав одного smoke (вариант A0)

Подготовка стенда (только объекты теста): каталог-приманка с наследованием как у `D:\` и вложенным файлом-канарейкой
(случайная строка); запись DENY для SID класса на корне приманки; тестовый ключ реестра с DACL как у
`HKCU\Environment` + DENY; поддельная «основная копия» с `.git`; соседняя попытка; каталог данных плагина
(существующий `guard_owner`).

| # | Действие воркера (или потомка) | Ожидается |
|---|---|---|
| T0 | живой токен: целостность, список restricting SID, привилегии | Low; точный список с SID класса; нет привилегии обхода прохода |
| P1 | изменить, создать, удалить файлы в своей `src`; писать в `home`, `temp` | успех; переменные окружения указывают внутрь попытки |
| P2 | дочерний `python`/`git.exe` пишет файл в `src` и в stdout | файл есть, вывод в capture owner |
| N1 | запись: файл «основной копии», её `.git/config`, файл соседней попытки, каталог данных плагина | ошибка 5 в каждом случае |
| N2 | чтение по пути: канарейка внутри приманки, список корня приманки, соседняя попытка, тестовый ключ | ошибка 5 |
| N3 | открытие канарейки по идентификатору файла с хендлом своего каталога | ожидается отказ; **успех = стоп, схема не годится** |
| N4 | жёсткая ссылка в `src` на канарейку | отказ |
| N5 | отдельная попытка B: junction в `src` на приманку | чтение через неё — отказ; capture B отказывает `ATTEMPT_REPARSE_POINT`, patch нет |
| N6 | отдельная попытка C: запись в `src/.git/hooks/…`, ненулевой код выхода | capture C отказывает по политике, patch нет, каталог сохранён, отказ записан |
| R1 | патч попытки A | ровно изменения P1/P2; политика и `git apply --check` на SHA проходят; SHA-256 записан |
| R2 | репетиция отката запрета на приманке тем же кодом снимка/отката | SDDL после отката = снимок |

Защита от ложного PASS:

- у каждого отказа есть положительный контроль: тот же объект тот же путь открывает процесс теста — цель
  существует, путь верен; засчитывается только код 5, не 2/3;
- воркер пишет отчёт по каждому шагу с порядковым номером; пропущенный шаг = FAIL;
- канарейка (случайная строка) в выводе воркера, capture или patch = FAIL;
- манифест хэшей основной копии до и после; retries 0; без `-k`; строки тестов и исходники сохраняются.

Регрессия: семь прежних native-файлов (17 проверок), потому что меняется состав токена.

**Не изолировано и не проверяется:** любой процесс того же пользователя со средней или низкой целостностью может
писать в каталог попытки, подменить patch до проверки, открыть воркер, продублировать хендл Job.

Ресурсы на момент этого разбора: свободно RAM 2,1 ГБ, файл подкачки 10,8 ГБ. Перепроверить непосредственно
перед запуском (пороги из CR: RAM ≥ 1 ГБ, подкачка ≥ 3 ГБ, D: ≥ 5 ГБ); `scripts/check` — только при RAM ≥ 4 ГБ.

## 6. Нужна ли правка CR и повторный gate

Да. Переход smoke на приманки, вынос применения к настоящим корням в отдельный шаг, план снимка/отката, заморозка
попыток и риск открытия по ID — существенные изменения scope и acceptance. По контракту гигиены существенная
правка возвращает CR в `HYGIENE_PENDING` и требует нового отчёта. Рекомендую одну правку и один gate после
ваших решений по Р1–Р4, а не две итерации.
