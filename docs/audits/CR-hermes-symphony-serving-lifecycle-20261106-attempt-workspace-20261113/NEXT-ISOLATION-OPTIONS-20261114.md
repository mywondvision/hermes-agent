# Варианты изоляции для первого реального driver (анализ, 2026-11-14)

Статус: рекомендация исполнителя. Ничего не менялось и не запускалось; HOLD сохраняются.

## Факты хоста (чтение, без изменений)

- Windows 11 Home 25H2, сборка 26200.9974; Ryzen 5 3550H, 4 ядра / 8 потоков, 13,9 ГБ RAM (свободно обычно 0,3–3 ГБ);
  C: 4,2 ГБ свободно, D: 694 ГБ; виртуализация в прошивке включена, гипервизор не запущен.
- Hyper-V и Windows Sandbox в редакции Home недоступны; WSL не установлен; VirtualBox/VMware/Docker не установлены.
- Codex CLI 0.167.0 (`D:\Codex\npm-global`). Встроенная песочница Windows уже есть: учётные записи
  `CodexSandboxOffline`/`CodexSandboxOnline` (режим `elevated` provisioned), в `D:\Codex\codex-home` выбран `unelevated`.
- Документация Codex (developers/learn.chatgpt.com, Windows sandbox и Permissions): режимы `mxc` (рекомендуемый; нужна
  сборка 26200.9278+ — у нас 26200.9974, на этом ПК не проверено), `elevated` (отдельные пользователи, ACL, firewall),
  `unelevated` (ограниченный токен, deny-read не поддерживает). Профили разрешений позволяют список разрешений:
  `":root" = "deny"`, `":minimal" = "read"`, workspace — `write`, сеть команд выключена. Трафик модели и авторизации
  идёт из самого клиента Codex, а не из команд песочницы. Команда `codex sandbox ... -- <cmd>` запускает любую
  команду в песочнице без модели.
- Доказанный обход: открытие по file ID обходит запрет на каталоге-предке. Обход не работает против проверки на самом
  объекте, то есть против списка разрешений (нужен SID/учётка в ACL самого файла или изоляция процесса).

## Рекомендация

Вариант 2: изоляцию команд делегировать встроенной песочнице Codex со списком разрешений; Hermes оставляет за собой то,
что уже доказано: одноразовая рабочая область без `.git`, копия на SHA, capture и политика patch, журнал, разрешения,
Job с kill-on-close для остановки клиента.

Короткий путь:

1. **Минимальная проверяемая граница (без модели, один проход).** `codex -c windows.sandbox=mxc sandbox --permission-profile <профиль>
   -- python <наш зонд>` на приманках: чтение по пути и по file ID, ключ реестра, запись вне попытки, сеть и loopback,
   дочерние процессы, остановка. Тот же зонд в `elevated` как запасной. Переиспользуются скрипт воркера, канарейка и
   положительные контроли из smoke attempt-workspace.
2. **Один ограниченный пилот.** `codex exec` на маленькой задаче в рабочей области попытки, профиль из шага 1, без MCP и
   web search, лимит бюджета; результат — patch, применение вручную.
3. **Расширение по результату**: размер задач, частота, применение patch через проверенный шаг.

## Решения владельца

1. Согласие делегировать изоляцию команд песочнице Codex и запускать сам клиент Codex с токеном пользователя (в Job).
   Это меняет прежнее правило «воркер никогда не стартует с токеном owner» для пути driver.
2. Авторизация модели для пилота: отдельный `CODEX_HOME` и способ входа (ключ API или вход ChatGPT), лимит бюджета.
3. Допуск на один no-model проход зонда (шаг 1).
4. Позже — допуск на пилот (задача, модель, effort, бюджет).

Агент решает сам: состав профиля, расположение рабочей области (`D:\SymphonyAttempts` по Р2), правки стенда, состав
зонда, доказательства.
