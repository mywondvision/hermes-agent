## Граница угроз первого сценария

Защищаемся от **воркера и его потомков**: они не изменяют чужие копии (рабочие деревья, `.git`, другие попытки,
данные плагина) и не читают секреты из согласованного владельцем списка.

**Ограничение (фиксируется, не решается этим CR):** схема не защищает от любого другого процесса того же
пользователя с обычными правами. Такой процесс имеет SID пользователя и среднюю целостность: он может писать в
каталог попытки, подменить patch до проверки, открыть процесс воркера и продублировать хендл Job из owner. Более
сильная граница требует другого субъекта безопасности — см. раздел «Если нужна более сильная граница».

Почему не `git worktree add` из kit: такое дерево ссылается на общий `.git` основной копии (объекты, refs,
hooks, config). Воркеру пришлось бы дать запись в `.git` или понизить его метку — оба варианта директива
запрещает, а записанные воркером hooks и config потом исполнил бы процесс со средней целостностью.

## Проверка чтения (факты, до CR)

Подробно: `docs/audits/CR-hermes-symphony-serving-lifecycle-20261106-attempt-workspace-20261113/READ-PREFLIGHT-20261113.md`.

- Текущий токен воркера по `AccessCheck` **читает** файл учётных данных Claude Code на D, `.env` другой копии,
  каталог приватных пакетов и `HKCU\Environment` (там ключи API пользователя); `.ssh` и `.codex` в профиле закрыты.
  Запись везде закрыта низкой целостностью.
- Причины: корень `D:\` даёт чтение группам Users и Authenticated Users с наследованием; `HKCU` даёт чтение
  `RESTRICTED`.
- Удаление только Authenticated Users ничего не меняет (читает Users). Удаление Users закрывает и системные
  DLL — процесс не стартует. RESTRICTED нужен для оконной станции и рабочего стола и оставляет чтение `HKCU`.
- Запись DENY для SID, который есть только в списке restricting SID воркера, даёт воркеру отказ и не
  затрагивает другие токены (проверено на собственном временном каталоге).

Минимально необходимые входы воркера: копия дерева на фиксированном SHA (без `.git`), интерпретатор с
библиотеками, системные DLL, дочерний инструмент, собственные HOME и TEMP. Учётные данные не входят и в каталог
попытки не копируются. Сейчас базовый интерпретатор тестового окружения лежит внутри рабочего дерева
(`.artifacts/test-appdata/uv/python/...`) — для воркера нужен интерпретатор вне защищаемых корней.

## Предлагаемое решение (предложение исполнителя, INFERRED; не решение владельца до `ok`)

1. **Корень попыток.** Owner создаёт один каталог-корень вне рабочих деревьев (кандидат `D:\SymphonyAttempts`,
   решение Р2) с защищённым DACL: пользователь, SYSTEM, администраторы; без наследования от `D:\`, без Users и
   Authenticated Users. Метка корня не понижается.
2. **Каталог попытки** `<корень>\<attempt>\` создаётся новым: подкаталоги `src` (копия дерева), `home`, `temp`.
   Доступ на изменение получают только SID пользователя и SID этой попытки; метка Low (OICI, no-write-up) ставится
   **только на этот новый каталог** — без неё воркер с целостностью Low писать не может. Метки и права
   существующих объектов (рабочее дерево, `.git`, данные плагина) не меняются.
3. **Копия дерева.** Owner выполняет `git -c core.autocrlf=false archive <SHA>` в основной копии (только чтение
   `.git` процессом owner) и распаковывает в `src`. `.git` в копию не попадает. Одновременно в приватном каталоге
   owner (данные плагина, метка NRNW) создаётся теневой Git-каталог: базовый коммит = то же дерево.
4. **Чтение секретов.** В список restricting SID добавляется один постоянный SID класса воркеров
   (`S-1-9-…` из фиксированной строки); `require_boundary` по-прежнему требует точный список. На согласованные
   защищаемые корни ставится одна запись DENY (чтение, список, проход) для этого SID, без наследования и без
   распространения на дочерние объекты. У токена воркера удаляется привилегия обхода проверки прохода, чтобы
   запрет на корне закрывал всё поддерево. Состав корней — решение Р1. До resume owner проверяет, что каждая
   запись на месте и `AccessCheck` токеном воркера даёт отказ; иначе отказ `READ_BOUNDARY_UNENFORCED`.
5. **Окружение воркера** — только явное: `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `TMP` внутри
   каталога попытки, `SYSTEMROOT`, `WINDIR`, `PATH` из согласованного списка. Переменные пользователя не
   наследуются; имена с признаками секрета отклоняются до создания процесса.
6. **Capture после остановки.** После выхода воркера и опустевшего Job owner:
   - обходит `src` без следования ссылкам и отказывает (`ATTEMPT_REPARSE_POINT`, `ATTEMPT_HARDLINK`), если найдена
     точка повторного разбора (junction, symlink) или файл с числом жёстких ссылок больше одного;
   - снимает diff теневым Git-каталогом: `GIT_DIR` и индекс — приватные owner, `GIT_WORK_TREE=src`,
     `GIT_CONFIG_NOSYSTEM=1`, пустой глобальный config, `core.hooksPath` в пустой каталог, без fsmonitor; ничего
     из `src` не исполняется и не добавляется в пути поиска модулей;
   - получает patch (`--binary`), проверяет политику: только разрешённые пути, без `.git*`, `.gitattributes`,
     `.gitmodules`, hooks и изменений режима исполнения, лимит размера;
   - проверяет `git apply --check` на свежей копии `<SHA>` в приватном каталоге owner, записывает SHA-256 patch
     и список путей в журнал наблюдений.
   Patch — данные. Применение к рабочему дереву вне этого CR.
7. **Удержание.** Каталог попытки и patch не удаляются автоматически (как `RETENTION_HOLD` в kit); удаление —
   только решением владельца.

Нового демона, IPC, очереди, HTTP, планировщика, переменных `HERMES_*`, учётных записей, AppContainer и
системных настроек нет. Пути отката на запуск без границы нет: любая невыполненная проверка — отказ.

## Существенные неизвестные

- Стартует ли Python без привилегии обхода проверки прохода и с SID класса в списке.

- Чтение остального `HKCU`, `C:\ProgramData` и прочих мест, доступных Users, Everyone или RESTRICTED, остаётся открытым.

- Работает ли настоящий driver на дереве без `.git` и что он пишет в свой каталог сессий — не измерено.

## Риски и rollback

- Запись DENY на пользовательских корнях — изменение хоста; затрагивает только токены с SID класса. Rollback: удалить записи.
- Срез может оказаться невыполнимым на этом хосте: результат — отказ запуска и запись причины, защита не понижается.
- Rollback кода: вернуть `plugins/symphony_pm/transport/` к `9ef69db2`; журнал и резервации не затронуты; каталоги попыток удерживаются до решения владельца.

- Р1. Защищаемые корни: **рекомендую** все каталоги верхнего уровня `D:\`, кроме корня попыток и каталога
  интерпретатора воркера, плюс `HKCU\Environment`; проверка до resume отказывает, если у какого-то каталога
  верхнего уровня записи нет. Узкая альтернатива: `D:\Claude`, `D:\AI\worktrees`, `D:\AI\preserve`,

- Р3. Удержание: каталоги попыток и patch не удаляются автоматически.
- Р4. Допуск на один native smoke (восемь файлов) и условие для корректирующего прохода. Исходное дерево smoke —
