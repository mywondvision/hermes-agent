# Hermes → Symphony: контракт для голосового интегратора

Дата: 2026-11-11. Основание: `docs/change-requests/CR-hermes-symphony-serving-lifecycle-20261106-continuation-20261111.md`.
Документ описывает, что голосовой контур может вызвать, какие ответы получит и что вправе сказать пользователю.
Он ничего не включает и не разрешает: transport не установлен, native/global cancel, release и настоящий stop
остаются **HOLD**. Утверждения сверены с кодом независимым ревью (`tools/symphony_pm_adapter.py`,
`plugins/symphony_pm/transport/`).

## 1. Что именно подключается

Единственная точка входа — существующий tool `symphony_pm_ingress` (toolset `symphony_pm`, контракт
`hermes-pm-ingress/v1`) внутри Hermes-сессии. Голосовой контур не получает отдельного API, очереди, HTTP-порта
или процесса.

**Кто что делает.** Голосовой слой доставляет в Hermes-сессию только распознанный **FINAL**-текст. Вызов tool
строит модель этой сессии: она выбирает `request_id`, `goal` и `raw_constraints`. Голосовой слой эти аргументы не
формирует и tool напрямую не вызывает. Полномочия приходят только из host-owned источника, привязанного к
profile + session + `request_id` + digest полезной нагрузки; любое расхождение даёт `WAITING_FOR_AUTHORITY`.
Какой именно production approval source показывает человеку точный payload — **UNKNOWN**, не закреплено (см. п. 4).

| Операция | Аргументы | Назначение |
|---|---|---|
| `submit_intent` | `contract_version`, `operation`, `request_id`, `project_ref`, `goal`, `raw_constraints` (массив строк, может быть пустым) — все обязательны | Записать одно намерение и, если transport подключён, выполнить одну попытку |
| `get_status` | общие четыре + `job_ref`, `expected_job_revision` | Последнее подтверждённое наблюдение |
| `request_cancel` | общие четыре + `job_ref`, `expected_job_revision`; `reason` необязателен | Запросить отмену; не подтверждение остановки. **Не подключать и не вызывать, пока HOLD на cancel не снят отдельным допуском** |

- Любое другое поле, включая поле чужой операции, даёт `REJECTED` (`UNKNOWN_FIELD`). Права, grant, issuer,
  session id, «confirmed: true», cwd в аргументах передать нельзя.
- `request_id`, `project_ref`, `job_ref`, `expected_job_revision` — по шаблону `[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}`;
  `goal` и `reason` — до 4096 символов; `raw_constraints` — до 32 строк по 2048 символов.
- `job_ref` и `expected_job_revision` берутся из `view.job_ref` и `view.job_revision` ответа на `submit_intent`.
- `get_status` и `request_cancel` требуют собственного host-разрешения на эту операцию и этот job; без него —
  `WAITING_FOR_AUTHORITY`.
- Partial ASR и текст модели grant не создают. Согласие, произнесённое голосом, grant не создаёт, если host не
  выбрал голосовой approval transport; код такого transport не содержит.

## 2. Ответ tool

При прямом вызове — JSON: `contract_version`, `outcome`, `hold`, `issues[]`, `operation`, `request_id`,
`payload_digest`, `view{}`. Если tool скрыт (transport недоступен на уровне toolset), вызов возвращает
`{"error": ...}` без этих полей — обрабатывать как `UNAVAILABLE`.

**`submit_intent` синхронный.** Ответ приходит после завершения попытки либо сбоя; вызов может длиться до
таймаута driver. `SUBMITTED` не означает «поставлено в очередь». Таймаут на стороне голосового слоя трактуется
как `UNKNOWN`.

**Правило `hold`.** `hold: true` означает «ничего не утверждать о выполнении и ничего не повторять
автоматически». `hold: false` **не** разрешает говорить «выполняется», «выполнено» или «остановлено» — допустимые
фразы заданы таблицей.

| `outcome` | `hold` | Что произошло | Что можно сказать пользователю |
|---|---|---|---|
| `UNAVAILABLE` (`NO_BACKEND`) | true | Transport не подключён (текущее состояние по умолчанию) | «Запуск задач сейчас недоступен» |
| `WAITING_FOR_AUTHORITY` | true | Нет подтверждённого разрешения на этот точный запрос | «Нужно подтверждение в Hermes» |
| `REJECTED` / `UNSUPPORTED` | true | Запрос отклонён до scheduler (форма, полномочия, версия, операция) | «Запрос отклонён», причина из `issues` |
| `CONFLICT` | true | Тот же `request_id` с другим содержимым | «Запрос конфликтует с уже записанным» |
| `SUBMITTED`, `view.scheduler_outcome = "SUBMITTED"` | false | Намерение записано, попытка вернулась без ошибки; `view.admission = NOT_CONFIRMED` | «Задача записана». **Не** «выполняется/выполнена» |
| `SUBMITTED`, `view.scheduler_outcome = "DUPLICATE"` | false | Этот запрос уже был принят раньше; исход прежней попытки этим ответом **не подтверждён** (она могла закончиться неизвестным исходом) | «Этот запрос уже был записан; состояние смотрите в Hermes». Ничего сверх этого |
| `STATUS` | true при `view.stage_acceptance = NOT_ACCEPTED`, иначе false | Наблюдение с доверенным происхождением | Ничего о ходе выполнения; см. ниже |
| `CANCEL_REQUESTED` | true | Запрос отмены принят | «Отмена запрошена». **Не** «остановлено» |
| `UNKNOWN` | true | Исход неизвестен **или** запрос не дошёл до запуска; причина — `view.uncertainty[0]` | «Состояние неизвестно, повтор не выполняется» |
| `UNVERIFIED` | true | Ответ scheduler не прошёл проверку | Как `UNKNOWN` |

Уточнения по текущей реализации serving port:

- **`get_status` сегодня возвращает `UNVERIFIED`** (`STATUS_PROVENANCE_UNVERIFIED`): доверенного источника
  наблюдений нет. `STATUS` появится только после его подключения.
- Когда `STATUS` появится: `view.phase` будет `UNKNOWN` или `LOCAL_STOPPED_HOLD`, при этом `hold` окажется false
  (`stage_acceptance = NOT_CLAIMED`). `UNKNOWN` значит «остановка не доказана», а не «работает»;
  `LOCAL_STOPPED_HOLD` значит «локальные процессы попытки прочитаны как завершённые», а не «задача остановлена».
  Фазу пользователю не озвучивать.
- **`view.age_seconds` всегда 0** и свежести не доказывает; о возрасте данных не говорить.
- `view.retention` содержит `["reservation", "POSSIBLY_CONSUMED_HELD"]`; `view.uncertainty` при успешном чтении
  содержит `EXTERNAL_AND_BILLING_UNKNOWN`. Значение «released» serving port не выдаёт.
- `CANCEL_REQUESTED`: `hold` стал бы false только при доверенных claims `worker_stopped`, `descendants_stopped`,
  `external_effects_settled`, `billing_settled` одновременно; serving port claims не выпускает, поэтому `hold`
  всегда true. Повторная отмена того же job возвращает `UNKNOWN`.

## 3. Обязательные правила поведения

1. **Один `request_id` на одно намерение.** Повтор того же намерения с тем же `request_id` и тем же содержимым
   не создаёт вторую попытку: ответ — `SUBMITTED` с `scheduler_outcome = "DUPLICATE"` (см. таблицу). Новый
   `request_id` на тот же текст новую задачу **не** создаёт — см. п. 2.
2. **Сейчас один namespace допускает один запуск.** Пока в namespace есть хотя бы одна запись о запуске
   (успешная, неопределённая или незавершённая), `submit_intent` с другим `request_id` возвращает `UNKNOWN`,
   `hold: true`, `view.uncertainty` содержит `UNSETTLED_PRIOR_LAUNCH_HOLD`. Новый запуск возможен только после
   ручной сверки владельцем. Это штатное состояние; обход запрещён.
3. **Никаких автоматических повторов** после `UNKNOWN`, `UNVERIFIED`, `CONFLICT`, таймаута или потери ответа.
4. **Отмена ASR, остановка записи, повторная клавиша и закрытие окна не являются отменой задачи** и не должны
   так озвучиваться. Они останавливают только голосовой ввод.
5. **STOP пользователя** всегда выполняется локально в голосовом слое (прекратить запись/воспроизведение) и не
   зависит от доступности Symphony, удалённого ASR или сети. Текстовый ввод остаётся запасным путём.
6. Только **FINAL** распознавания может стать текстом сессии; partial — нет. Пустой FINAL, ошибка ASR и
   отклонение worker'ом не доставляются в сессию.
7. Пока идёт синхронный `submit_intent`, голосовой слой показывает «работаю» и не доставляет в ту же сессию
   повтор той же фразы.
8. Голосовой слой не читает и не пишет journal, lock-файлы и каталог `plugin-data/symphony_pm`, не открывает
   процессы и Job Objects попытки, не вызывает Codex напрямую от имени этого контура.
9. Смена набора tools или system prompt посреди разговора не допускается: подключение transport видно только
   новым сессиям.

## 4. Условия подключения (все обязательны)

| Условие | Состояние на 2026-11-11 |
|---|---|
| Owning host устанавливает `ServingBinding` до приёма conversations (plugin discovery сам ничего не запускает) | Код есть, не установлен |
| `QualificationRecord` совпадает с profile, namespace, scheduler, issuers, ревизией kit, путём и SHA-256 исполняемого файла, ссылкой и SHA-256 окружения | Проверка реализована и покрыта fixture-тестами; реальной записи квалификации нет |
| Конкретный production approval source, показ точного payload человеку и доставка в request binding | **UNKNOWN**, не закреплён |
| Доверенный источник наблюдений для `get_status` | Отсутствует |
| Точный допуск владельца: model / effort / environment / attempt | Не выдан; запрос — `docs/audits/CR-hermes-symphony-serving-lifecycle-20261106-continuation-20261111/PERMIT-REQUEST-20261111.md` |
| Job воркера недоступен процессам из дерева воркера | **Не выполнено.** Открытие по имени убрано и проверено native-проходом, но synthetic-воркер с токеном owner продублировал хендл Job из процесса owner с правом менять лимиты. На 2026-11-12 подготовлен прототип: воркер рождается с ограниченным токеном низкой целостности, запуск отказывает, если границу нельзя построить или проверить. Offline-проверки пройдены. 2026-11-13 один native-проход без модели прошёл (`5 files, 15 tests passed, 0 failed`; один прогон, один хост). Независимое ревью: закрыт путь дублирования Job из owner; выход из Job через соседей, брокеры и loopback не исследован. Пункт остаётся **невыполненным**. Второй native-проход 2026-11-13 (`7 files, 17 tests passed, 0 failed`): воркер больше не может открыть процесс owner и не может читать, менять или блокировать журнал; но **подтверждён выход из Job** — воркер создал процесс вне своего Job подменой родителя на соседний процесс с низкой целостностью. Production-пути записи для воркера по-прежнему нет |
| Воркер не читает лишние секреты пользователя | **Не выполнено.** Прототип ограничивает запись и доступ к owner, но не чтение файлов пользователя и не сеть |
| Повторный запуск в том же namespace (исправление после ревью вторым запуском) | Недоступен: после любого запуска действует `UNSETTLED_PRIOR_LAUNCH_HOLD`, settlement и release остаются HOLD |
| Допуск на native/global cancel и настоящий stop | Не выдан; `request_cancel` не подключается |
| Глобальная голосовая активация, живая русская речь, ASR FINAL/cancel | Отдельный контур, этим CR не затрагивается |
| `plugins.isolation: host` | Для стороннего плагина регистрация runtime-сервиса отклоняется и serving недоступен; для bundled-плагина изоляция не применяется. Тестами не покрыто |

Пока хотя бы одно условие не выполнено, корректный ответ tool — `UNAVAILABLE`/`WAITING_FOR_AUTHORITY`, и голосовой
слой обязан работать с ним как с штатным состоянием.

## 5. Что голосовому контуру нельзя утверждать

- что задача запущена, выполняется или завершена — по `SUBMITTED` в любом варианте и по `STATUS`;
- что worker остановлен — по `CANCEL_REQUESTED`, по `LOCAL_STOPPED_HOLD`, по отмене ASR;
- что данные свежие — по `view.age_seconds`;
- что ресурсы освобождены или начисления прекращены — никогда (billing и внешние последствия UNKNOWN);
- что отмена «гарантирована» или «мгновенна».

## 6. Прямой CLI-путь

Безопасный прямой CLI-путь голосового контура (собственный интерпретатор и рабочее дерево) от этого контракта не
зависит и им не блокируется: он не использует tool `symphony_pm_ingress`, journal и owner lock. Работы по
lifecycle его каталоги не изменяют.

Граница: находка о хендле Job относится к общему механизму запуска воркера в Job. Если прямой CLI-путь начнёт
запускать исполнителя через этот механизм (`symphony_pm` transport, `LifecycleOwner`, `WindowsReceiver`), на него
распространяются те же HOLD и условия п. 4. Пока он этот механизм не использует, HOLD его не касается.

## 7. Изменение контракта

Любое изменение `outcome`/`view`, правил п. 3 или условий п. 4 оформляется отдельной поправкой CR. Версия
контракта tool — `hermes-pm-ingress/v1`; несовпадение версии — `REJECTED`.

## 8. Статус доказательств на 2026-11-12

- Fixture: `11 files, 144 tests passed, 0 failed` (на 2026-11-11 было `10 files, 136`).
- Synthetic native no-model (свои Python-процессы, без повторов): первый проход `2 files, 11 tests passed, 0 failed`;
  после среза доступа к Job — `2 files, 12 tests passed, 0 failed` и диагностический зонд `1 files, 1 tests passed`.
- Прототип границы воркера (ограниченный токен): native-проход 2026-11-13 — `5 files, 15 tests passed, 0 failed`;
  после усиления границы — `7 files, 17 tests passed, 0 failed`, диагностика подтвердила выход из Job через соседа.
- Настоящий driver, модель, native/global cancel и настоящий stop не запускались и остаются **HOLD**.

Известное ограничение tool: JSON-схема `symphony_pm_ingress` перечисляет в `required` только четыре общих поля,
поэтому модель может не знать, что `goal` и `raw_constraints` обязательны; такой вызов вернёт `REJECTED`.
