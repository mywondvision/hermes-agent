# Linux owner-check для Ruff и pytest

Этот документ относится к отдельному Linux-профилю Hermes Symphony и проверке непустого patch без модели. Тесты в Windows-worktree подтверждают работу кода с фиктивным диспетчером. Нативная приёмка проходит на выделенной Linux-ВМ после отдельного допуска владельца.

## Комплект для ВМ

Пути ниже предназначены для развёртывания. Владелец образа или администратор ВМ подготавливает комплект. Владелец Symphony принимает результаты квалификации и подключает checker к конкретному профилю.

| Компонент | Путь и назначение |
|---|---|
| Шаблон службы | `/etc/systemd/system/hermes-symphony-check@.service`. Шаблон из `plugins/symphony_pm/transport/systemd/` запускает по одному доверенному контроллеру на invocation. |
| Интерпретатор контроллера | `/opt/hermes-symphony/controller/bin/python3` в закреплённом образе контроллера. |
| Вход контроллера | `/opt/hermes-symphony/controller/hermes-agent/plugins/symphony_pm/transport/linux_check_entry.py`. Systemd передаёт путь manifest и идентификатор экземпляра. |
| Конфигурация checker | `/etc/hermes-symphony/owner-check.json`. Администратор привязывает профиль, разрешённые команды, исполняемые файлы и лимиты к конкретному комплекту. |
| Свидетельство квалификации | `/etc/hermes-symphony/owner-check-evidence.json`. Пригодное свидетельство появляется только после проверки на соответствующей ВМ. |
| Образ среды | `/opt/hermes-symphony/check-runtime`. Защищённый read-only образ содержит Python, pytest и Ruff. Проверочные команды получают подготовленную копию исходников только для чтения и отдельную временную область. Git-зависимые проверки откладываются. |
| Управляющие записи | `/var/lib/hermes-symphony/check-control`. Приватный каталог для намерений запуска и квитанций. |
| Одноразовые копии | `/var/lib/hermes-symphony/check-scratch`. Отдельный каталог владельца для применённого к копии patch, теневого индекса Git и файлов подготовки. |

В доверенном коде старта профиля фабрика `plugins.symphony_pm.transport.linux_systemd_check.systemd_owner_check(qualification)` создаёт backend. Хост передаёт его как `owner_check` в `linux_serving_bootstrap(...)` загруженного плагина и настраивает сервис `('symphony_pm', 'ingress-linux')`. Пустой профиль сохраняет инертный инструмент. Конфигурацию и свидетельство читает доверенный процесс владельца.

Администратор образа предоставляет системные `systemctl` и `bwrap`, выделенного пользователя и группу `hermes-symphony`, делегированное поддерево cgroup v2 и квотированный scratch. Точные пути системных программ и хэши фиксируются в manifest. Независимый оператор квалификации собирает свидетельства видимости файлов, изоляции сети и временных данных, отсутствия Git, доступа к управляющим сокетам и учётным данным, остановки дерева и восстановления квитанции после рестарта. В root-owned evidence входят ссылки по хэшу на девять свидетельств, привязанные к проверенному host, boot и политике. Фиктивные квитанции из тестов для установки непригодны.

В поставляемом шаблоне выбраны начальные лимиты `RuntimeMaxSec=120`, `TimeoutStopSec=8`, `MemoryMax=512M`, `TasksMax=128` и `CPUQuota=100%`. Допустимый размер отдельного scratch-тома задаётся в manifest. Эффективные значения systemd входят в квалификацию. Изменение шаблона или бюджета требует обновить её до допуска следующих проверок.

Manifest версии 1 содержит объекты `installation` и `profile`. Точный набор полей и проверок определён в [linux_check_config.py](../../../plugins/symphony_pm/transport/linux_check_config.py). Сначала вычисляется digest политики по версии, installation и profile без поля `evidence_sha256`. Затем независимый оператор фиксирует в evidence этот digest и хэши нативных свидетельств. В `profile.evidence_sha256` записывается SHA-256 точных байтов получившегося файла. Разрешённые команды задаются списком относительных путей для `ruff check` либо `python3 -I -B -m pytest`. Срок одной команды задаётся в профиле и ограничен 90 секундами.

## Восстановление места после остановки checker

Для каждой команды владелец создаёт отдельную копию. Перед dispatch он сохраняет в `owner-check.active` идентификаторы исходной попытки, команды, эпохи, профиля и каталога. Полученную точную квитанцию он записывает в приватные данные попытки как `check-stop-<nonce>.json`. Маркер остаётся на диске до проверки и удаления каталога с исходной идентичностью и синхронизации его родителя. Несколько команд одного плана получают разные копии одного и того же дерева.

После рестарта владелец сопоставляет маркер с исходной записью журнала. Совпавшая локальная квитанция позволяет завершить очистку, даже если служба уже собрана. При отсутствии квитанции допускается только наблюдение исходного invocation. Замена каталога по прежнему пути, конфликт квитанций или неподтверждённая остановка сохраняют HOLD. Проверка обрабатывает только каталог из маркера. Произвольные соседние `c-*`, включая старые остатки без привязки или копию, оставшуюся при сбое до dispatch, требуют отдельной сверки владельцем по исходному invocation и идентичности каталога.

## Что проверять после допуска на нативную кампанию

- Подтвердить версию образа, систему запуска, права выделенного пользователя, эффективные параметры службы и соответствие разрешённых команд установленным Ruff и pytest.
- Сверить контрольные файлы и каталоги, видимые из настоящей песочницы, отдельное сетевое пространство, режим чтения дерева и лимиты scratch, времени, CPU, памяти и процессов.
- На одном безмодельном patch проверить отдельные успешные команды Ruff и pytest. Сопоставить исходный commit, SHA-256 patch, фактическое дерево проверки и номер CAPTURE с квитанцией CHECK.
- Проверить ненулевой код команды, таймаут, незавершённый процесс-потомок и перезапуск владельца. Для освобождения слота требуется квитанция об остановке именно исходной службы и её cgroup. Неопределённый исход сохраняет HOLD и первичный результат.

При выборе среды для сопоставимых измерений использовать закреплённые входы из `docs/audits/PLAN-hermes-symphony-to-release-20261118/ACCEPTANCE-WINDOWS-LINUX.md` и `benchmark_preflight.py` в ревизии документов `79a4ce37967c`.
