# Установка коннектора Responses для CR-LINUX

Комплект предназначен администратору выделенной Linux-ВМ с systemd и cgroup v2. Развёртывание и проверка подписки требуют отдельного допуска владельца. Исходники и unit берутся из одного принятого Git-архива. Офлайн-тест использует временный сертификат, фиктивные заголовки и TLS-сервер на loopback.

Текущий коннектор покрывает только передачу Responses. Для холодного запуска клиента остаются открыты получение политики подписки и разделение пользователей доверенного реле и исполняемой команды. При таком устройстве системы контроллер должен отказать в допуске до резервирования попытки. Порядок ниже описывает подготовку компонента для будущей квалификации.

## Файлы и права

| Что подготовить | Размещение и проверка |
|---|---|
| Образ коннектора | Отдельный read-only squashfs по `/opt/hermes-symphony/connector`, без вложенных монтирований. Администратор фиксирует SHA-256 файла образа. Компоненты путей принадлежат root и защищены от записи другими пользователями. Формат loop mount и доступ к backing file должны удовлетворять `linux_sandbox.verify_image`. |
| Интерпретатор | Обычный файл `/opt/hermes-symphony/connector/bin/python3` с изолированной стандартной библиотекой Python 3.11+ из образа. Квалификация охватывает версию Python, OpenSSL, используемые системные библиотеки и DNS выделенной ВМ. Интерпретатор должен разрешать свою стандартную библиотеку из закреплённого образа при запуске с `-I -S`. |
| Точка входа | Байты `plugins/symphony_pm/transport/linux_responses_connector.py` из архива копируют без преобразований в `/opt/hermes-symphony/connector/bin/responses-connector`. Владельцем файла служит root. Python открывает его для чтения. |
| Корни доверия | PEM-файл одобренных администратором публичных корневых сертификатов внутри образа по `/opt/hermes-symphony/connector/etc/ssl/certs/ca-certificates.crt`. Клиент TLS требует доверенную цепочку и совпадение имени `chatgpt.com`. Обновление CA требует нового образа и квалификации. |
| Unit | Байты `plugins/symphony_pm/transport/systemd/hermes-symphony-connector.service` копируют в `/etc/systemd/system/hermes-symphony-connector.service` с владельцем root и режимом 0644. Требуется самостоятельная служба с `Type=exec`, без drop-in и socket activation. |
| Сервисная учётная запись | Выделенные пользователь и основная группа `hermes-symphony`. Служба коннектора использует `User=root` и `Group=hermes-symphony` с пустым набором capabilities. systemd создаёт каталог `/run/hermes-symphony-connector` с владельцем root, группой `hermes-symphony` и режимом 0750. Процесс службы привязывает `responses.sock` с режимом 0660. |

Метод, upstream, порт и проверка TLS закреплены в точке входа. SHA-256 её байтов — `9c26e3a3577774b6e50fa9c3ee4daaf041f721faca1623de47bf7fa41cac2f8c`. SHA-256 unit — `752ff5d8f8a6c599ce12b0f7da6c8b0f698736725f74f6dd833f181055056737`.

## Порядок допуска

1. Сопоставить SHA-256 файлов точки входа и unit из принятого Git-архива с установленными файлами. Зафиксировать SHA-256 образа, интерпретатора и системного `systemctl`. Точный запуск службы приведён в её `ExecStart`.
2. После разрешённой установки загрузить unit в systemd и запустить его. Сверить `FragmentPath`, `DropInPaths`, `ExecStart`, `MainPID`, `InvocationID`, время создания процесса, владельца и режим сокета. Записать идентичность загрузки, сетевого пространства хоста и inode сокета. Новый запуск службы требует свежей привязки свидетельства.
3. Сверить видимость сокета и файла подписки из доверенного реле и песочницы команды. При подключении сервер получает PID, UID и GID от ядра через `SO_PEERCRED`. Допускается выделенная учётная запись реле и путь cgroup v2 `/system.slice/…/hermes-symphony@<64 hex>.service/payload`. Между корневым slice и службой допускаются лишь имена slice. Для этой проверки коннектору требуется чтение `/proc/<peer-pid>/cgroup`. Песочница команды должна скрывать Unix-сокет, файл подписки и TCP-адрес реле.
4. Для первой проверки настоящего Linux CLI использовать [порядок квалификации на синтетической подписке](PROVIDER-QUALIFICATION.md). На той же Vast VM со штатным SSH весь стенд, включая коннектор, запускается в отдельном сетевом пространстве службы с одним loopback. При будущей приёмке рабочего сервиса потребуются отдельные свидетельства допуска конкретного процесса, отсутствия дочерних процессов на запрос, закрытия upstream при разрыве реле и опустошения исходной cgroup. Закрытие TLS подтверждает завершение местного соединения. Судьба удалённого запроса и начисления требуют собственных подтверждений.

## Пределы соединения

Коннектор принимает один HTTP/1.1 POST на `/backend-api/codex/responses` с единственным `Host: chatgpt.com`, Bearer, идентификатором подписки, типом `application/json` и точным Content-Length. Перечень допустимых заголовков задан в исходнике. Прямой TLS-клиент сам задаёт имя, порт 443 и путь. Выходной трафик выделенной ВМ должен допускать разрешение имени и HTTPS к этому сервису. Служба отбрасывает перенаправления и смену протокола. В журнал службы данные запроса и ответа не выводятся.

На соединение действуют пределы 32 КиБ для блока заголовков, 16 МиБ для запроса и 64 МиБ для ответа. Одновременно обслуживаются до четырёх запросов. Приём запроса и ожидание отдельных операций ограничены десятью секундами, общий срок составляет 300 секунд. SSE передаётся по мере поступления. Обрыв соединения реле отменяет обмен, в том числе во время ожидания первого заголовка ответа. Остановка всей службы прекращает все активные соединения.
