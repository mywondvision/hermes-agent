## 1. Что есть сейчас (as-is)

```
 модель в сессии Hermes
   │ tool symphony_pm_ingress {submit_intent | get_status | request_cancel}
   ▼
 ServingIngress (service.py) ── authority_source = ApprovalSource.__call__ (только чтение permit)
   │        нет permit → adapter без контекста → WAITING_FOR_AUTHORITY, порт не вызывается
   │                                       ▲
   │                                       │ record_permit ← ApprovalSource.request_permit  (никто не вызывает)
   ▼                                       │
 SymphonyPmAdapter (tools/symphony_pm_adapter.py, ядро) → ServingPort (port.py)
   ▼
 LifecycleOwner (lifecycle.py) ── Journal SQLite v1 (journal.py, schema.py)
   │  guard: WindowsOwnershipGuard   observer: WindowsQueryObserver (открывает каждый процесс Job)
   │  submit() ─ синхронно ─► CodexExecLauncher(ticket, request, runner)
   ▼
 CodexExecLauncher: копия коммита в <attempts>/active → codex sandbox (предпроверка, свой Job)
   → runner → CodexClientProvider: codex.exe с токеном пользователя, suspended, Job kill-on-close
   → codex exec под MXC-профилем → capture patch (теневой git) → owner-check (без песочницы) → result в журнал
   ▼
 hermes symphony status (status_cli.py) — чтение журнала mode=ro
```

## 2. Целевая схема (to-be)

```
 Человек-владелец ── slash-команды /symphony … в своей сессии (приходят входящим сообщением, не от модели, D4)
        ▲  точный план + digest                  │ approve / deny / stop / release / apply
        │                                         ▼
 модель ─► symphony_pm_ingress ─► ServingIngress ─► AuthoritySource
                                    │               ├─ ApprovalBroker  (submit: показать план; permit — по команде человека)
                                    │               └─ ControlGrants   (status/cancel своего job, D3)
                                    ▼ PlanResolver (host-side: project_ref → repo/ветка/source_sha, D5)
                                 ServingPort ─► LifecycleOwner ── Journal v2 (терминальные состояния + наблюдения)
                                    │ submit: durable-резерв, ответ SUBMITTED сразу
                                    ▼
                                 RunSupervisor (один поток на namespace, создан на старте сервиса, D1)
                                    ▼
                                 CodexExecLauncher
                                   ├─ precheck: codex sandbox (env по allow-list, D7)
                                   ├─ exec: codex.exe (токен пользователя, Job kill-on-close) → MXC
                                   ├─ stop-proof: Job пуст по учёту владельца (D14) — до capture
                                   ├─ capture: теневой git, повторяемый из сохранённой попытки (D8)
                                   └─ OwnerCheck: codex sandbox с профилем проверки (D6)
                                    ▼
                                 терминал запуска: NOT_STARTED | STOPPED(proof) | HELD_UNKNOWN → namespace (D2, D13)
                                    ▼
 status: одна проекция журнала → /symphony status, CLI (read-only) и get_status (D9)
 apply:  /symphony apply от человека → commit-tree в ветку symphony/<job>, без checkout и push (D10)
```

**Модель угроз B2 (честно, ред. 2).** При локальном терминале (F26) агент работает от того же пользователя, что и
владелец Symphony. Тогда он может не только писать в `journal.sqlite3` и запускать `hermes symphony …`, но и
**запустить клиент Codex напрямую** с тем же входом по подписке и без песочницы, вообще минуя Symphony (INFERRED:
файлы дома Codex принадлежат тому же пользователю). Следствия:

1. В профиле с локальным терминалом, записью файлов или исполнением кода подтверждение Symphony — это ограждение
   от непреднамеренного запуска и аудит, но **не граница безопасности**. Никакой fixture и никакая подпись permit
   этого не изменят: секрет, доступный процессу gateway, доступен и терминалу того же пользователя.
2. Границей оно становится только в профиле, где у агента нет инструментов, исполняющих код или пишущих файлы на
   хосте от пользователя (нет локального терминала, `execute_code`, записи файлов; либо терминал в контейнере/SSH).
3. Решение владельца (Q11, 2026-11-19): агентам нужен терминал. **Временно принят риск (б)**: подтверждение
   Symphony на пилоте — ограждение и аудит, не граница безопасности; это записывается в CR-7 и в отчёт пилота.
   Целевое состояние — выделенный профиль с терминалом, ограниченным папкой проекта (D17), отдельный CR-7b; он
   обязателен до релиза (CR-10).
4. Независимо от Q11: все команды CLI плагина только читают (ничего, что стоит запускать из терминала агента);
   подтверждения в памяти процесса gateway и не переживают рестарт (другой процесс не может их «дожать»).

### 2.2 Инварианты (из `AGENTS.md`), которые план не нарушает

1. **Prompt caching.** Инструмент появляется или исчезает только на границе старта хоста: сервис стартует до
   приёма разговоров (`runtime-services.md:8-11`, F12). `wire()/unwire()` в живом пути не используются
   (перерегистрация посреди процесса — F12). Статус, итог попытки и запрос подтверждения приходят результатом
   вызова инструмента или **новым** сообщением (D16), никогда правкой system prompt или прошлого контекста.
   Оговорка (INFERRED): сессия, начатая до включения и продолженная после рестарта, увидит изменённый список
   инструментов один раз; то же при неудачном старте сервиса (F15/F16 → инструмент скрыт) — поэтому отказ
   старта должен быть виден оператору (`hermes symphony doctor`, CR-6).
2. **Узкое ядро.** Новых core-инструментов и новых seams ядра план не добавляет: включение (D11), канал
   подтверждения (D4), уведомления (D16) строятся на существующих generic-поверхностях (F24). Остаётся решение о
   текущем следе в ядре (F11, Q1).
3. **Профили.** Работа вне хода (RunSupervisor, settle, reconcile) создаётся в точке, где scope дома уже связан
   (фабрика сервиса, F25), через `spawn_context_thread`; пути берутся из `scope.profile_home`, не из окружения
   процесса; дочерние процессы владельца получают окружение по allow-list (F25).
4. Без новых `HERMES_*` env; поведение — в `config.yaml`; `.env` — только секреты.
5. Тесты — через `scripts/run_tests.sh`; native — `@pytest.mark.platforms("windows")` на этом хосте; ratchet
   размеров (функции ≤ 300 строк, файлы ≤ 2000, новое поведение — в sibling, не в фасаде).
6. **Один хост — одна попытка** (F23), пока каталог `active` и профиль MXC единственные.

## 3. Решения

Каждое решение — PROPOSED, пока владелец не дал `ok` на CR, который его реализует. Основания помечены отдельно.

**D1. Асинхронный запуск (RunSupervisor).** `submit` делает durable-резерв и возвращает `SUBMITTED` с `job_ref`;
launcher выполняет один поток на namespace. Уточнения ред. 2: (1) поток создаётся **на старте сервиса** под scope
дома (F25) через `spawn_context_thread`, а не из хода — иначе он унаследует контекст конкретного хода; в этой
точке связан дом профиля, связан ли scope секретов — не проверялось: владельцу он не нужен, и чтение секрета из
потока должно оставаться ошибкой (INFERRED, тест в CR-5); (2) задание
передаётся потоку в памяти, не через журнал: резерв, не подхваченный до смерти процесса, никогда не запускается
позже (сохраняет «no queue, no auto-resume» из `lifecycle.py:3-5`) и при reconcile получает `NOT_STARTED`;
(3) поток не ходит через порт и adapter (полномочие запроса не пересекает поток — `plugin_request_binding.py:96-103`),
а работает с владельцем по сохранённому `WriterToken` (fencing — `lifecycle.py:145-148`); (4) остановка — через
`scope.on_close`; после неё запись результата невозможна (F27), это покрывает D13. Альтернативы: (a) оставить
синхронно — ход блокируется до 40 мин (F1/F1a); (b) отдельный процесс-демон — второй владелец журнала и Job,
конфликт с fencing; (c) фоновые процессы терминала Hermes — запуск мимо владельца и журнала. Рекомендация: поток в
процессе-владельце. Меняет принцип «no worker thread» — решение владельца (Q3). Основание F1 — CONFIRMED.

**D2. Журнал v2: терминальные состояния запуска отдельно от конвейера результата.** Ред. 1 предлагала одну цепочку
`… EXITED → CAPTURED|CAPTURE_FAILED → CHECKED → SETTLED`; в ней освобождение namespace зависит от capture и
проверки, а состояние после `CAPTURE_FAILED` не определено. Предлагается разделить две оси:

- *Запуск* (держит namespace): `LAUNCH_INTENT → CREATE_INTENT → BOUND → RESUME_INTENT`, затем терминал:
  `NOT_STARTED` (слот create не занят; ставится атомарным переходом из `LAUNCH_INTENT`, после которого
  `claim_create` невозможен — F19), `STOPPED` с видом доказательства `JOB_EMPTY | OWNER_DEAD | BOOT_CHANGED`
  (D13, D14), `HELD_UNKNOWN` (стоп не доказан) и `RELEASED_BY_OWNER` (человек снял удержание, D4).
- *Результат* (не держит namespace): append-only наблюдения `EXIT`, `CAPTURE`, `CHECK`, `APPLY` с номером
  попытки наблюдения (D8). Неудачный capture — это наблюдение, а не тупик состояния.

Namespace свободен ⇔ в нём нет нетерминальных строк **и** каталог `active` отсутствует (F23; при отказе
переименования — удержание с причиной `WORKSPACE_HELD`). Название `NEVER_ENTERED_OS` из ред. 1 неточно для отказа
предпроверки (она входит в ОС, F19) — терминал называется `NOT_STARTED`. Хранение: терминальное состояние и поля
доказательства в той же таблице `serving_launches`, проверка удержания — «есть нетерминальная строка» вместо «есть
строка»; отдельная таблица истории (ред. 1) не нужна и ломала бы чтение статуса завершённых job. Наблюдатель
покрывает только нетерминальные строки (снимает F16). Миграция v1→v2 — только схема: состояний она не выводит,
существующие строки остаются нетерминальными до reconcile по D13. Permit не возвращается: новый запуск — новое
подтверждение. Альтернатива «несколько одновременных запусков» отклонена (F23, память хоста). Основания F5, F16,
F19 — CONFIRMED.

**D3. Политика status/cancel.** submit — подтверждение человеком точного плана. `get_status` и `request_cancel`
своего job из той же сессии — без человека: подтверждение запуска покрывает наблюдение и остановку (отмена только
сужает эффект). Механика (ред. 2, из F2/F21): отдельных строк permit для контроля нет; `authorize_control` получает
ветку «полномочие, производное от записи запуска» (совпадают сессия, job, revision), не зависящую от срока permit
запуска и от наличия binding (статус `NOT_STARTED` и статус после истечения permit должны читаться). Человек
управляет любым job своего профиля через `/symphony status|stop` (D4) — это и запасной путь, если `session_id`
сменился (INFERRED-риск: стабильность `session_id` между ходами и при сжатии контекста не проверена; проверка —
в CR-6). Альтернатива: человек на каждый статус и отмену — непригодно для опроса (F2). Решение владельца: Q4.

**D4. Канал человека — slash-команды плагина в сессии владельца.** Требование: модель не может сама подтвердить.
Ред. 1 рекомендовала approval transport поверх Telegram-кнопок и CLI-команды, «создающие запрос в канал». Ред. 2:

- (a, рекомендация) `ctx.register_command("symphony", …)`: `/symphony approve|deny <код>`, `stop`, `release`,
  `apply`, `recapture`, `status`. Команда приходит входящим сообщением человека, обрабатывается в процессе gateway
  (там же, где владелец и handle Job), получает `source` и `session_key` (F24); работает на всех поверхностях
  (gateway-платформы, TUI, CLI) без правки ядра и без IPC. Для `approve` — тот же отправитель и та же сессия, что
  у запроса, плюс код из показанного плана (префикс digest). Ограничение (F24): в gateway команда
  диспетчеризуется, только когда сессия свободна, — поэтому подтверждение неблокирующее (D5a), а `stop` из той же
  сессии во время её собственного хода не сработает (при D1 сессия во время попытки обычно свободна).
- (b) inline-кнопки Telegram через `ctx.register_telegram_handler` с `pattern=` — только одна платформа, зато
  обработчик не зависит от занятости сессии (INFERRED); дополнение после (a), прежде всего для `stop`.
- (c) CLI-команда в другом процессе — отклонено: процесс CLI не владеет Job и журналом (нужен IPC), и это ровно та
  поверхность, которую может вызвать терминал агента (B2).
- (d) локальное окно Windows — вне поверхности плагина, не работает для удалённого владельца.
- (e) выбрать transport глобально через `security.approval.transport` — отклонено: перехватит все подтверждения
  Hermes (`tools/approval_prompt.py:207-212`).

Следствие: блокирующий `request_permit` поверх `hermes_cli.approval_transport` (`approval.py:29-64`) для этого
канала не используется; permit пишет обработчик команды через запись permit владельца, читающая часть
`ApprovalSource.__call__` остаётся. Это отступление от формулировки handoff («`ApprovalSource` +
`approval_transport`»). Проверить в CR-6/CR-7 на реальном пути входящих команд: (1) для plugin-команд нет
admin-политики (F24) — привязка к отправителю запроса делается в обработчике; (2) модель не может породить входящую
slash-команду (INFERRED); (3) поведение в TUI и CLI (INFERRED). Решение владельца: Q5.

**D5. PlanResolver.** `ExecutionPlan` строит хост, не модель: `project_ref` → запись проекта в `config.yaml`
профиля; `source_sha` — commit ветки-источника в момент запроса подтверждения; `workspace` = `<attempts>/active/src`;
`model`/`effort` = `codex-config` (F10). Модель передаёт только `project_ref`, `goal`, `raw_constraints`. Ред. 2:
transport сейчас привязан к одному репозиторию (F23), поэтому пилот — **один проект**; для нескольких проектов план
получает поле `repository_ref` (значение по умолчанию сохраняет чтение старых строк) — отдельный CR после пилота.
Человеку показывается: проект, репозиторий, ветка, `source_sha`, полный текст `goal` и ограничений, лимит времени,
срок действия; срок permit покрывает ожидание, экспорт и предпроверку (F22; PROPOSED 15 мин). Альтернатива: план из
аргументов модели — отклонено (B1). Что builder отсутствует — CONFIRMED (F3).

**D5a. Как submit ждёт подтверждения.** Ред. 1 рекомендовала: первый submit возвращает `UNKNOWN`/hold с причиной
`APPROVAL_PENDING` «из существующего исхода adapter», модель повторяет `request_id`. Это не соответствует коду:
без permit источник полномочий возвращает `None`, порт не вызывается, adapter отвечает
`WAITING_FOR_AUTHORITY`/`TRUSTED_CONTEXT_ABSENT` (`service.py:86-91`, `tools/symphony_pm_adapter.py:742-743`);
получить `UNKNOWN` от порта без контекста нельзя. Кроме того, у схемы с повтором нет ответа на вопрос, кто
разбудит модель после подтверждения. Варианты:

- (a, рекомендация) неблокирующий: первый submit публикует план в чат и сразу возвращает
  `WAITING_FOR_AUTHORITY`; ход заканчивается, сессия свободна; человек отвечает `/symphony approve <код>` (idle-путь,
  F24) — обработчик пишет permit; модель повторяет тот же `request_id` и получает резерв и `SUBMITTED` (при D1 —
  сразу). Запуск остаётся внутри авторизованного запроса модели (`service.py:38-41` не меняется). Отложенный запрос
  живёт в памяти процесса со сроком (рестарт = отказ). Кто будит модель: ответ команды человеку («подтверждено,
  попросите агента продолжить») и, по флагу, сообщение в сессию (D16). Если модель не повторила запрос до истечения
  permit — запуска нет, нужно новое подтверждение (F22).
- (b) «подтверждение запускает»: обработчик `approve` сам делает резерв и запуск, модель позже получает
  `DUPLICATE` с `job_ref`. Меньше шагов для человека и нет гонки со сроком permit, но появляется запуск вне
  запроса модели — второй путь к владельцу. Кандидат на замену (a) после пилота; выбор владельца (Q12).
- (c) блокирующее ожидание внутри вызова submit до 300 с, как встроенные подтверждения Hermes
  (`tools/approval_prompt.py:246-250`). Со slash-командами в gateway **невыполнимо**: пока ход занят вызовом
  инструмента, plugin-команда не диспетчеризуется (F24); к тому же нужны внутренние помощники ядра (F1a).
  Возможно только с кнопками Telegram (D4(b)).

Запрос подтверждения инициирует `ServingIngress.handle` (там есть разобранный intent, `service.py:76`), а не
`authority_source(identity)` — тому intent не передаётся. Любой вариант означает, что вызов инструмента порождает
обращение к человеку, — уточнение правила `approval.py:30-34`, решение владельца (Q12). Один ожидающий запрос на
сессию; повтор того же `request_id` во время ожидания не создаёт второй запрос и второе сообщение.

**D6. Owner-side проверка в песочнице.** `ruff` и тесты без git запускаются через `codex sandbox` с отдельным
профилем проверки (запись только в каталог копии проверки, сеть выкл.). Тесты, которым нужен `git`, переносятся в
шаг apply (D10) и запускаются только после решения человека. Ред. 2: сама `git apply` в копию проверки остаётся на
стороне владельца — это работа git над данными в каталоге без репозитория, с отключённой системной и глобальной
конфигурацией (`codex_exec_launcher.py:459-461`, `attempt_workspace.py:126-129`), код patch при этом не
исполняется (INFERRED); окружение дочерних процессов владельца — allow-list (F25).
Альтернатива: оставить как есть (F8). Метка: PROPOSED.

**D7. Окружение команд песочницы.** Зонд записывает полный список имён переменных; `probe_ok` требует, чтобы он был
подмножеством утверждённого набора (тот же принцип, что allow-list клиента, `codex_exec_launcher.py:103-110`).
Альтернатива: фильтр по именам — уже пропустил вебхук (RESULT шага 2). Открытая находка 2 — CONFIRMED.

**D8. Наблюдения вместо перезаписи результата.** Итог хранится как неизменяемая запись запуска плюс append-only
наблюдения. Повторный capture/проверка из сохранённой попытки — команда человека без модели. Ред. 2, условия
реализуемости (CONFIRMED по коду): текущий `Capture` для повтора непригоден как есть — теневой каталог создаётся
без `exist_ok` (`attempt_workspace.py:147-150`), baseline сравнивает рабочее дерево с коммитом (`230-238`) и после
запуска уже не сойдётся, файл patch открывается в режиме «только создать» (`253`). Повтор — отдельный путь: новый
теневой каталог на каждое наблюдение, база = дерево `source_sha` (равенство baseline доказано при запуске и
записывается в наблюдение), имя результата с номером наблюдения. Сохранённая попытка лежит в каталоге того же
пользователя: доверие к повтору то же, что в B2. Главная ценность повтора — попытка, оборванная рестартом (F27).
Альтернатива: разрешить перезапись `result` — теряется первичная запись. F9 — CONFIRMED.

**D9. Доверенный статус.** Одна функция-проекция журнала для `/symphony status`, CLI и `get_status`. Ред. 2
снимает неопределённость ред. 1 (её «альтернатива» — наблюдение со своим временем — невыполнима из-за F20):
источник полномочий **до** вызова порта делает чтение владельца (проекция журнала; для идущей попытки — учёт Job),
записывает его строкой наблюдения с временем `now` и кладёт в контекст `TrustedObservation` с тем же `now`,
`evidence_ref` = идентификатор этой строки и `trusted_producers` = владелец; порт строит receipt из той же строки
журнала. Для завершённой попытки добавляется `TrustedCompletion` с проверками стадии песочницы; `required_checks`
— именно эта стадия (git-тесты относятся к apply), в выдаче это `stage_acceptance`. Честная оценка: в одном
процессе с одним владельцем независимого второго источника нет — проверка adapter подтверждает, что ответ порта
равен долговечной записи владельца, а не внешнему наблюдателю. Фазы — строки проекции: `PENDING`, `RUNNING`,
`NOT_STARTED`, `STOPPED`, `HELD_UNKNOWN`, а из набора «готово» adapter (`DONE_PHASES`) — только при наличии
результата. Отмена: `worker_stopped` и `descendants_stopped` подкрепляются доказательством `JOB_EMPTY`; внешние
эффекты и биллинг недоказуемы, поэтому ответ отмены всегда с hold (F20). Контракт adapter не меняется (F6).

**D10. Применение patch.** Только командой человека `/symphony apply <job> <префикс sha256>` (D4). Ред. 1: новый
worktree, apply, git-тесты, commit. Ред. 2 предлагает меньший эффект: patch сверяется с SHA-256 из журнала;
commit строится без рабочего дерева — временный индекс, `read-tree source_sha`, `apply --cached`, `write-tree`,
`commit-tree` (приём с временным индексом уже используется проверкой применимости, `attempt_workspace.py:204-210`).
Отличие от неё: объекты должны писаться в хранилище **целевого** репозитория, а не теневого каталога попытки —
иначе ссылка ветки укажет на объекты, которых в целевом репозитории нет. Git-тесты идут в
экспорте дерева нового commit (вне песочницы, уже после решения человека); затем create-only `update-ref
refs/heads/symphony/<job>`. Не затрагиваются HEAD, индекс и рабочее дерево владельца; не выполняются hooks и
checkout-фильтры репозитория (worktree их запускает). Без push, без защищённых веток, без автоприменения; повтор —
no-op с той же веткой; провал git-тестов — ветка не создаётся, наблюдение записано (обход — явный флаг человека).
Альтернативы: worktree (ред. 1); применение в рабочую копию владельца — смешивает patch с правками человека.
Учесть guard `tests/conftest.py` против `git apply` в настоящем checkout (память проекта, 2026-11-14).

**D11. Включение в живой сессии — без нового seam ядра.** Ред. 1 рекомендовала новый generic-seam: хост читает
`config.yaml` и вызывает фабрику binding плагина. Ред. 2 рекомендует вариант (b): фабрика сервиса плагина (она уже
выполняется на старте хоста под scope дома, F25), когда `scope.binding is None`, читает секцию плагина в
`config.yaml` (под существующим корнем `plugins.entries.<id>`, как флаг injection — `hermes_cli/plugins.py:624-632`;
загрузчик — тот, что использует gateway, по правилу `hermes_cli/AGENTS.md`; INFERRED: ключи внутри записи плагина
не требуют регистрации в defaults ядра — проверить в CR-9a) и сама собирает transport; без секции — инертна. Причины: (1) ноль новых файлов ядра
(правило «plugins never touch core», F11); (2) seam из (a) функционально тождествен — тот же код плагина, вызванный
на шаг раньше, а единственный его потребитель — Symphony; (3) `ServiceHost.configure` остаётся для встраивающих
хостов и тестов. Цена: уточнить текст `runtime-services.md:41` — конфигурация включает *механизм* (transport и
канал человека), но не выдаёт grant: каждый запуск по-прежнему подтверждает человек (D4). Квалификация (хэши
клиента и профиля MXC, F10) хранится в конфигурации профиля; агент с записью файлов мог бы её переписать — это тот
же случай B2/Q11. Вариант (c) — отдельный процесс `hermes symphony serve` — отклонён: второй хост без чата.
Действует со следующего старта хоста (инвариант 1). Решение владельца: Q6.

**D12. Платформа и ресурсы.** Только Windows 11 с MXC, плагин in-tree (F13). Лимиты Job клиента: 64 процесса, 6 ГБ
(`codex_client.py:47`, CONFIRMED). Минимум свободной RAM на попытку — PROPOSED ≥ 4 ГБ (INFERRED из падений
`0xC0000142` при < 1 ГБ); проверяется до резерва (`doctor`, D15). Жёсткий лимит попытки — время
(`exec_timeout`); расход токенов сейчас виден только после запуска (`codex_exec_launcher.py:430`); остановка по
порогу в ходе запуска — PROPOSED, требует проверки формата событий (CR-9b).
Ред. 3 (Q8, Q7): эксплуатация и пилот — на **арендованной машине**; лимит попытки — 120 мин (сейчас 40, константа
`codex_exec_launcher.py:199` → значение из секции конфигурации плагина). Следствия: (1) transport работает только
на Windows с MXC (Job objects, `codex sandbox`) — арендованная машина должна быть Windows 11 или Windows-ВМ, где
`codex sandbox` проходит зонд; Linux-аренда (GPU-провайдеры) не подходит без переноса transport, который вне
плана (INFERRED: работа MXC на Windows Server не проверялась). (2) Квалификация, профиль MXC и хэши — на машину;
стенд с моделью (CR-8a) и всё после него — на целевой машине. (3) Один бот Telegram нельзя опрашивать двумя
gateway одновременно (INFERRED) — на время пилота нужен отдельный бот или остановка gateway на этом хосте.
Подготовка машины — CR-H.

**D13. Восстановление: смерть владельца и смена boot — доказательство стопа.** Сейчас оба случая — вечное
удержание (F15, F16), а комментарий кода прямо отказывается от вывода (`lifecycle.py:127-131`). Предлагается
правило reconcile при старте владельца: (1) прежний процесс-владелец того же boot доказанно мёртв (pid + время
создания, `windows_ownership.py:46-64`) ⇒ все его handle Job закрыты ядром ⇒ kill-on-close остановил дерево (F18)
⇒ нетерминальные строки с занятым слотом create → `STOPPED(OWNER_DEAD)`, с незанятым → `NOT_STARTED`;
(2) `boot_id` сменился ⇒ процессов прежнего boot не существует ⇒ `STOPPED(BOOT_CHANGED)`, запись владельца
заменяется; (3) осиротевший `active` после доказанного стопа переименовывается в имя попытки из журнала;
(4) результата у таких строк может не быть — его добирает `recapture` (D8). Основание: семантика ядра и native-тесты
краша (F18). Остаточный риск (INFERRED): процесс, запущенный от имени клиента вне Job (служба, планировщик) — для
MXC проверяется native в CR-4. Альтернатива: оставить удержание и снимать его человеком (`/symphony release`)
после каждого рестарта с незавершённой строкой. Это отступление от решений прежних CR — решение владельца (Q13).

**D14. Доказательство стопа — пустой Job по учёту владельца.** Текущий наблюдатель обязан открыть каждый процесс
Job (F7), а процессы команд MXC работают под другими учётными записями (INFERRED: открыть нельзя). Тогда
наблюдатель «нездоров» именно тогда, когда нужна отмена, и остановка недоступна (F7). Предлагается для transport
`codex exec` отдельная реализация `QueryObserver` (sibling в плагине; `WindowsQueryObserver` и путь воркера не
меняются): handshake — Job зарегистрирован и корень в нём; чтение — учёт Job (число активных и список pid,
`windows_api.py:148-160`) и сигнал корневого процесса. Процессы-члены не открываются. Проверка
`LifecycleOwner._local_stop` (`lifecycle.py:274-292`) при этом не меняется: она требует `job_active == 0`, пустой
список членов и сигнал известных процессов. Порядок завершения попытки (и при выходе 0, и при TIMEOUT/отмене):
`TerminateJobObject` (если Job не пуст) → ограниченное ожидание пустоты → запись доказательства → закрытие handle
Job → **затем** capture (снимает F17). Если пустоту прочитать не удалось — handle закрывается (kill-on-close),
состояние `HELD_UNKNOWN`. Корректность опирается на F18 (нет breakaway, handle не наследуется). Альтернативы:
(a) оставить UNKNOWN и полагаться на закрытие Job при выходе gateway — попытка работает без лимита (F7);
(b) повышенные права наблюдателя — расширение привилегий владельца. Метка: PROPOSED; native-проверка — CR-4.

**D15. Операторская поверхность.** Запись — только slash-команды (D4). CLI — только чтение: `hermes symphony
status` (есть) и `hermes symphony doctor` (новая): причина, по которой владелец не стартовал бы (F15/F16 до
D13, расхождение хэшей квалификации, занятый `active`), свободная RAM и диск, число и объём сохранённых попыток.
Хранение попыток (каждая — копия дерева, копия проверки, теневой git): счётчик и порог предупреждения; удаление —
только командой человека `/symphony prune`, без автоудаления (как в CR шага 2). Ред. 3 (Q15): раз в неделю
отдел сам предлагает список на удаление (сообщением по D16(b): сколько попыток, объём, какие); удаление — только
после `/symphony prune approve <код>` от владельца. Никогда не удаляются: `active`, попытки в `HELD_UNKNOWN`,
попытки с непримененным patch младше срока, заданного в конфигурации. Метка: PROPOSED.

**D16. Уведомление о завершении.** При D1 результат появляется вне хода. Варианты: (a) опрос — человек
`/symphony status`, модель `get_status`; (b) `ctx.inject_message(..., session_key=)` (F24): новое сообщение в
сессию, открывшую job, — фиксированный шаблон (job, состояние, SHA-256 patch, итог проверки), **без** свободного
текста Codex (это недоверенный вывод модели). Не мутирует прошлый контекст (инвариант 1). Требует явного opt-in
`allow_gateway_injection` в конфигурации профиля. Решение владельца (Q14): **(b) включается** (флаг в профиле
Symphony), (a) остаётся всегда. Реализация — CR-9a.

**D17. Профиль эксплуатации.** См. модель угроз B2. Ред. 2 предлагала профиль без исполнения кода и записи
файлов. Владелец (Q11): агентам нужен терминал. Ред. 3: цель — выделенный профиль Hermes для Symphony, где
терминал агента есть, но **ограничен папкой проекта** и не видит дом Codex, журнал Symphony и каталоги попыток.
Кандидаты (INFERRED, выбор в CR-7b): (1) тот же MXC (`codex sandbox`) как среда терминала агента — уже
квалифицирован на хосте, запрещает корень и сеть; (2) отдельная учётная запись Windows с ACL только на папку
проекта; (3) контейнер или SSH-среда терминала Hermes (`tools/environments/`). Пока CR-7b не закрыт — принятый
риск (б), записан в CR-7. Один проект (D5); один хост — одна попытка (F23).

**D18. Голос (ред. 3, Q9 и Q5).** Владелец: голосовой контур (Bimo) готов и нужен сейчас. Решение: голос — только
**канал ввода**: доставляет в сессию Hermes распознанный FINAL-текст (как в контракте голосового интегратора
2026-11-11); через него можно поставить задачу и спросить статус. `approve`, `apply`, `release`, `prune` голосом
сейчас **не принимаются**: распознанный текст подделывается проще (чужая речь рядом с микрофоном, ошибка ASR).
Обработчик `/symphony` отклоняет эти команды, если сообщение пришло из голосового источника (как отличить
источник — проверить в CR-V1, INFERRED). Контракт голосового интегратора переписывается под v2 (асинхронный
`SUBMITTED`, `WAITING_FOR_AUTHORITY`, терминалы журнала v2, фразы). Подтверждение голосом, которое нельзя
подделать, — отдельный доверенный интерфейс Bimo (CR-V2, после пилота). Каталоги голосовой сессии
(`.artifacts/s4-global-voice-20261106/prepared/`) план не трогает. Альтернатива: принимать `approve` голосом
сразу — отклонено до CR-V2. Метка: PROPOSED.
