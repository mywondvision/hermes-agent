## Варианты поставки и изоляция

- **Fork, выбран по Q1.** Оставить общие сервисы хоста, привязку запроса, точки жизненного цикла и факт Windows в Hermes. Держать предметный контракт и код Symphony в собственном каталоге плагина. Условия запуска serving остаются явными: `ServiceHost.configure()` принимает объект привязки до старта профиля, а без него `ServingIngress` оставляет инструмент инертным. В `e8f2879d` общие вызовы запуска `start_host_services()` сами этот объект не устанавливают. `e8f2879d:AGENTS.md:20–25,40–46,56–59,133`; `e8f2879d:plugins/AGENTS.md:7–15`; `e8f2879d:hermes_cli/plugin_services.py:196–228,248–251`; `e8f2879d:plugins/symphony_pm/service.py:53–71`.
- **Форма для upstream.** Правила допускают расширение общего `ctx` с конкретным потребителем и помещают новые плагины для сторонних продуктов в отдельные репозитории. Возможный вклад состоит из обоснованных общих API с тестами совместимости и документацией. Допустимость каждой общей части и её принятие определяются отдельно сопровождающими upstream. Для `windows_boot.py` в изученной ревизии найден ровно один продуктовый потребитель, и его выделение для upstream требует самостоятельного обоснования. `e8f2879d:AGENTS.md:34–59`; `e8f2879d:plugins/AGENTS.md:7–15,52–55,150–173`.
- **Отдельный репозиторий плагина.** Место поставки соответствует правилу upstream для стороннего продукта. Для текущей serving-схемы нужны совместимый Hermes с этими API, перенос адаптера и поддержанный контракт для вызовов, которые сейчас импортируются из внутренних путей. Само вынесение репозитория таких API не добавляет. `e8f2879d:plugins/AGENTS.md:52–55,166–173`; `e8f2879d:plugins/symphony_pm/__init__.py:37–43,79–87`; `e8f2879d:plugins/symphony_pm/service.py:12–18,53–71`.

**F13.** При `plugins.isolation: host` отдельно установленный non-bundled плагин загружается в изолированный процесс профиля. Его `RemotePluginContext` отказывает в `register_runtime_service` и `register_approval_transport`; принимающая сторона также отклоняет эти методы. `getattr(ctx, "register_runtime_service", None)` в существующем `register()` получает функцию, которая при вызове поднимает `PluginHostUnsupported`. Это отличается от загрузки на старом хосте, где метод отсутствует: текущая регистрация отдельного плагина при `host` заканчивается ошибкой загрузки. `register_approval_transport` — отдельное уже существовавшее ограничение, текущая регистрация Symphony вызывает `register_runtime_service`. Bundled-копия fork в этот удалённый путь не попадает. Для отдельной поставки с нынешним контрактом нужен разрешённый оператором `in_process`; совместимость с закреплённым режимом `host` потребует отдельного проекта изменения границы. `e8f2879d:plugins/AGENTS.md:116–148`; `e8f2879d:hermes_cli/plugins_loader.py:613–625,655–658`; `e8f2879d:hermes_cli/plugin_isolation.py:35–44`; `e8f2879d:hermes_cli/plugin_host_child.py:97–107`; `e8f2879d:hermes_cli/plugin_host.py:402–408`; `e8f2879d:plugins/symphony_pm/__init__.py:79–90`.

## `wire()` и `unwire()` (F12)

В исходном коде `register()` ставит инертную регистрацию. Ручной `wire()` заменяет её регистрацией с заданным портом и источником полномочий, `unwire()` регистрирует инертный вариант снова. Оба меняют поколение реестра. Путь `ServingIngress` при наличии host binding ставит собственный обработчик в фабрике сервиса с `check_fn`, зависящим от `scope.active`. После успешной фабрики scope активируется, при shutdown/unload допуск закрывается до удаления registrations. Сам обработчик проверяет активность scope и полномочие даже при прямом вызове. `e8f2879d:plugins/symphony_pm/__init__.py:20–28,66–90,93–118`; `e8f2879d:plugins/symphony_pm/service.py:34–50,53–96,112–123`; `e8f2879d:hermes_cli/plugin_services.py:41–59,112–134,185–193`.

**Решение CR-0.** Сохранить обе функции внутри плагина для существующего ручного контракта и offline-тестов. `wire()` допустим при подготовке до первой беседы, `unwire()` — при завершении после прекращения обслуживания бесед. В штатном serving доступность устанавливается при старте сервиса, а при выгрузке или остановке `ServiceScope` закрывает приём запросов и освобождает регистрацию через ledger. Вызовы посреди беседы меняют регистрацию, которую видят последующие обращения к реестру. У уже созданного агента есть собственный список схем, поэтому смена обработчика и вычисление нового набора схем могут произойти в разные моменты. Из этого следует граница использования для стабильного набора инструментов и prompt cache. В изученной ревизии эти функции не проверяют, обслуживается ли беседа. Граница входит в решение CR-0, механический перенос в CR-0b сохраняет существующее поведение. `e8f2879d:AGENTS.md:20–23`; `e8f2879d:agent/agent_init.py:1035`; `e8f2879d:hermes_cli/plugins_activation.py:1–8`; `e8f2879d:tools/registry.py:752–768,928–965`; `e8f2879d:model_tools.py:832`; `e8f2879d:tests/plugins/test_symphony_pm_ingress_offline.py:121–134`; `e8f2879d:tests/plugins/test_symphony_pm_plugin.py:327–333`.

## Проверка и зависимость CR-0b

По `--name-status` и `--stat` сверены все 16 путей. Назначение и решения проверены по диффам и потребителям в фиксированных Git-объектах. Состав результата ограничен документальной инвентаризацией. Закрытие CR-0 требует отдельного результата независимого ревью.

После закрытия CR-0 отдельно согласуется обязательный **CR-0b**. Он переносит адаптер и его тесты, обновляет все импорты и ссылки на старый путь, включая `from tools import symphony_pm_adapter`, сохраняет контракт и проверяет fixture-набор и отсутствие предметного модуля в `tools/`. CR-0b проходит до старта линий A и B. Основание — `3a5ec102:docs/change-requests/PLAN-hermes-symphony-to-release-20261118.md:123–134`.
