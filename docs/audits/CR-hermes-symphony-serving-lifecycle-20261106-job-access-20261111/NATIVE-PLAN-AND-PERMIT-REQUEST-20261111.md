# План native-проверки и запрос допуска: доступ к Job Object воркера

Дата: 2026-11-11. CR: `docs/change-requests/CR-hermes-symphony-serving-lifecycle-20261106-job-access-20261111.md`.
Этот документ — запрос, а не допуск. Прежний допуск на native-проход израсходован; до нового ответа владельца
ни один файл `tests/plugins/test_symphony_pm_windows_*.py` не запускается.

## Этап N1 — synthetic no-model (запрашивается сейчас)

| Параметр | Значение |
|---|---|
| Что запускается | `tests/plugins/test_symphony_pm_windows_native.py` и `tests/plugins/test_symphony_pm_windows_crash.py`, целиком, одним вызовом `scripts/run_tests.sh -j 1 --file-retries 0 --file-timeout 300 … -v` |
| Число проходов | ровно один; повтор при любом исходе требует нового допуска |
| Процессы | только собственные процессы Python из существующего тестового окружения и их console host; ни Codex, ни другие исполняемые файлы |
| Модель / driver | нет; CodexDriver и launcher не участвуют |
| Среда | существующее тестовое окружение без установки пакетов; отдельные HOME, USERPROFILE, APPDATA, LOCALAPPDATA, TEMP, HERMES_HOME, HERMES_RUNTIME_DIR в новом каталоге прохода; `UV_OFFLINE=1`, `HERMES_DISABLE_LAZY_INSTALLS=1`; новый пустой каталог `HERMES_E2E_ARTIFACTS`; оболочка без повышенных прав |
| Лимиты | Job воркера: не более 2 активных процессов; containment Job теста: не более 4; файл — 300 с, весь проход — 900 с; сеть, микрофон, платные ресурсы не используются |
| Cleanup | только средствами ядра: kill-on-close Job воркера и containment Job теста; тесты не завершают процессы по PID и не выполняют «уборку сирот»; после прохода проверяется, что containment Job пуст и хендлы закрыты |
| Фиксация | манифест SHA-256 исходников до и после; лог; `result.json`; proofs; при таймауте — `outcome=TIMEOUT`, состояние дочерних процессов UNKNOWN, без повтора |

Что этот проход доказывает:

1. Job воркера нельзя открыть по прежнему детерминированному имени: `OpenJobObjectW` возвращает
   `ERROR_FILE_NOT_FOUND` (новый тест в `test_symphony_pm_windows_native.py`).
2. Observer читает состав Job через дубликат хендла с правом `JOB_OBJECT_QUERY`; `IsProcessInJob` и чтение
   списка процессов работают на таком хендле.
3. Kill-on-close сохраняется: в трёх срезах сбоя owner (после create, перед resume, после эффекта отмены) ядро
   останавливает воркер без участия теста.
4. Преемник записывает `CREATE_UNBOUND_UNOBSERVED`, не запускает повторно, журнал не меняется.
5. Takeover, fencing и запрет второго отправителя отмены ведут себя как в проходе от 2026-11-11.

Чего этот проход не доказывает:

- что воркер, исполняющий произвольные команды, не получит хендл Job дублированием из процесса owner;
- что настоящий driver совместим с удерживаемым хендлом исполняемого файла;
- ничего о native/global cancel, release и настоящем stop.

## Этап N2 — адверсариальный synthetic-воркер (отдельный допуск, после решения по токену)

Нужен новый тест, которого сейчас нет: дочерний процесс внутри Job воркера пытается (а) открыть Job по
идентификатору попытки и (б) открыть процесс owner с `PROCESS_DUP_HANDLE` и продублировать хендл Job. Ожидание
для (а) — отказ. Для (б) при текущей модели (тот же пользователь, тот же токен) ожидается **успех**, то есть
подтверждение остаточного риска. Этап имеет смысл только вместе с решением владельца:

- запускать воркер с ограниченным или другим токеном, либо
- ужесточить DACL процесса owner, либо
- принять риск явно для заданного класса задач.

До этого решения находка считается суженной, не закрытой.
