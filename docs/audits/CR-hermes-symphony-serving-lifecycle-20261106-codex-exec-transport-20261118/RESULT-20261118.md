## Найдено: секрет в окружении клиента (директива владельца)

В A3 окружение клиента строилось фильтром по именам (`KEY|TOKEN|SECRET|…`). Фильтр пропустил переменную с
URL вебхука (`*_WEBHOOK`) и строку подключения в клиент Codex. Имена в публичных материалах не приводятся.

Команды песочницы получают окружение по `shell_environment_policy.inherit = "core"`. В pilot 2 при той же
политике полный список имён в предпроверке содержал только core-набор. Значит, команды модели эти
переменные, по всей видимости, не получили. В A3 полный список имён не записывался, поэтому для этого
запуска вывод косвенный.

Клиенту владелец доверяет, но директива требует проверки. Исправлено в `be91e303`: окружение клиента теперь
allow-list стандартных имён Windows плюс собственные `CODEX_HOME`, HOME и TEMP; добавлен fixture-тест.
Рекомендация для следующего CR: зонд должен записывать полный список имён, а `probe_ok` — сверять его с
core-набором.

## Риски и открытое

- Путь TIMEOUT: `cancel_internal` читает участников Job наблюдателем. Процессы песочницы MXC работают под
  другими учётными записями и могут не открыться на чтение. Тогда отмена даёт UNKNOWN, а остановку
  гарантирует только закрытие Job в `LifecycleOwner.close()`. Native-тест на это не запускался: на него
  нет допуска.
- Процессы, которые owner-сторона запускает при проверке (ruff, тесты из patch), работают с токеном
  пользователя без песочницы. Так решено в RESULT pilot 2; это остаётся риском до шага 6.
- Каталог `D:\SymphonyAttempts\attempt-…` хранится без автоудаления (по CR).
- HOLD без изменений: production-источник разрешения (шаг 3), доверенный `get_status` (шаг 4),
  cancel/stop и закрытие попытки (шаг 5), автоприменение patch (шаг 6), deploy, merge, голос.
